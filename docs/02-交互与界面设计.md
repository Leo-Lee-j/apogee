## 1. 设计目标

界面设计服务于 PRD 的两条原则：**性能是功能** 和 **键盘优先**。具体转化为三条可检验的设计约束：

1. **首屏只画必要的东西**：冷启动首帧渲染的 DOM 节点数 < 800。侧边栏、编辑器、响应区都懒挂载。
2. **视觉噪音预算**：主界面同时可见的可点击元素 ≤ 40 个。超过就要砍或折叠。
3. **每个高频操作 ≤ 2 步**：发请求 1 步（`Ctrl+Enter`），切环境 2 步（`Ctrl+E` → 选），新建请求 1 步（`Ctrl+T`）。

## 2. 信息架构

```
Apogee
├── 工作区 Workspace（对应本地一个目录，可多开窗口）
│   ├── 集合 Collection（一个子目录）
│   │   ├── 文件夹 Folder（可嵌套）
│   │   │   └── 请求 Request
│   │   ├── 集合级配置：变量 / 鉴权 / 脚本 / 请求默认值
│   │   └── 集合级文档 README
│   ├── 环境 Environment（dev / staging / prod ...）
│   │   ├── 普通变量
│   │   └── 密钥变量（钥匙串存储）
│   ├── 全局变量
│   ├── Cookie Jar（按域）
│   ├── 历史 History（时间轴，含请求/响应快照）
│   └── 运行记录 Runs（Collection Runner 结果）
└── 应用级
    ├── 设置（外观 / 网络 / 代理 / 证书 / 快捷键 / 数据目录）
    ├── 命令面板
    └── 性能自检面板
```

**关键设计决策**：只有 4 层组织层级（工作区 → 集合 → 文件夹 → 请求）。Postman 里「Workspace / Team / Collection / Folder / Request / Example」六层是认知负担的主要来源之一。

### 3.3 三种布局模式

用户可切换（`Ctrl+Shift+L` 循环）：

1. **上下分栏**（默认）：适合看长 JSON
2. **左右分栏**：适合宽屏，请求和响应并排
3. **专注模式**：隐藏侧边栏和标签栏，只留 URL + 响应，适合排查单个接口

## 4. 关键区域交互设计

### 4.1 URL 栏 —— 全产品最重要的一行

```
┌─────────┬──────────────────────────────────────────────┬──────────┬────────┐
│ GET   ▾ │ {{baseUrl}}/users/:id?expand=profile         │ 发送  ▾  │ 保存   │
└─────────┴──────────────────────────────────────────────┴──────────┴────────┘
              ↑ 变量高亮（绿=已解析 红=未定义）
              ↑ hover 变量显示：baseUrl = https://api.dev  (来源: 环境 dev)
```

设计要点：

- **方法选择器颜色语义**：GET 绿、POST 蓝、PUT 橙、PATCH 紫、DELETE 红、HEAD/OPTIONS 灰。颜色 + 文字双通道（无障碍要求）。
- **URL 是一个轻量代码编辑器**，不是 `<input>`：需要变量高亮、变量补全（输入 `{{` 弹出候选）、Path 参数识别。
- **智能粘贴**：粘贴 cURL 命令 → 自动询问「检测到 cURL，是否导入？」，一键填充方法/URL/Header/Body。粘贴完整 URL 带 query → 自动拆到 Params 表。
- **发送按钮下拉**：`发送并下载`、`发送 N 次`（压测轻量版）、`导出为 cURL`、`发送并新建标签`。
- **Path 参数联动**：URL 里写 `:id` 或 `{id}`，Params 面板自动出现 Path 参数行，不用手动加。

### 4.2 请求编辑区与只读接口文档

打开请求后，请求主面板提供「编辑 / 文档」两种查看模式。**文档模式是当前请求配置的只读 UI 投影，不是独立的 API 文档管理平台**：不提供编辑、协作、发布或版本管理，也不替代 URL 栏、响应区和实际请求快照。

#### 4.2.1 切换入口

位置候选对比：

| 候选位置 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 请求区 32px 工具栏最右侧 | 与被替换区域同属一个面板；所有编辑 Tab 下位置稳定；上下/左右布局都可见 | 需要为模式控件预留固定宽度 | **采用** |
| 作为 Params/Headers/Body 的同级 Tab | 实现简单 | 文档是整个请求的查看模式，不是某一类参数；会混淆 Tab 语义 | 不采用 |
| URL 栏发送/保存按钮附近 | 最醒目 | 与发送、保存争夺产品最重要的一行，且作用域看起来包含整个请求/响应工作区 | 不采用 |
| 参数表 `section-head` | 离内容近 | 只在 Params/Headers 中出现，Body/Auth 下入口消失；容易理解成只切换当前表 | 不采用 |
| 顶部请求标签栏 | 可跨页面保留 | 离被替换区域太远，并会把请求内视图状态提升成全局动作 | 不采用 |

采用紧凑的文字两态控件，不使用只有书本图标的按钮。工具栏顺序固定为「编辑 Tab → 当前 Tab 上下文动作 → 分隔 → 模式切换」：

```text
编辑态：Params  Headers  Body  Auth  Settings      [批量编辑] │ [编辑 | 文档]
文档态：接口说明 · 只读                                        [编辑 | 文档]
```

- 模式控件固定在最右侧，切换前后不位移；文档态隐藏编辑 Tab，避免它们看起来仍在切换文档章节。
- 窄面板下优先让左侧 Tab 横向滚动，右侧模式控件不收进溢出菜单，也不退化成纯图标，保证始终一键可达。
- 控件使用原生按钮组语义（组名「请求区查看模式」，选中项使用 `aria-pressed`），不能与左侧 `role="tablist"` 混成同一个 Tab 集合。
- 不增加模式切换动画；只替换工具栏左侧内容和下方主体，URL 栏、请求/响应分栏比例、响应区内容都保持不动。

#### 4.2.2 状态与切换规则

1. 新打开的请求默认进入「编辑」，避免用户误以为参数不可修改。
2. 模式按**请求 Tab**在当前会话内记忆；切换请求再切回来时保持原模式。该状态不写入请求 YAML、不参与保存、不触发 dirty；关闭 Tab 或退出工作区时清理。
3. 文档直接投影当前内存态，包含尚未保存的修改；有未保存内容时在「当前配置」旁显示 `有未保存修改`，不悄悄回退到磁盘版本。
4. 在批量编辑中切到文档时**不应用批量草稿**，避免只读模式切换产生编辑、dirty 标记或磁盘写入；文档继续展示当前 Tab 配置，并提示「批量编辑草稿未应用」。返回编辑后保留草稿，用户点击「完成」或「取消」决定是否提交。
5. 返回编辑时恢复离开前选中的 Params/Headers/Body/Auth/Settings Tab；焦点落到模式控件，键盘用户可继续操作，不尝试聚焦已经卸载的输入框。
6. 文档内容可选择文本，也允许复制**不含参数实际值的接口地址模板**；复制不是修改操作。文档主体中不得出现请求示例值、请求体原文、`<input>`、`<textarea>`、`contenteditable`、删除、排序或保存按钮。

#### 4.2.3 文档格式

首版使用**单列、自然滚动的结构化接口说明 UI**，延续请求面板现有的 Apogee 视觉语言；它解决开发对接时快速确认接口结构的需求，但不仿制 Swagger/OpenAPI 的独立文档站界面。页面不使用 Markdown 原文、富文本编辑器、OpenAPI 表单、嵌套 Tabs 或默认折叠卡片。原因是请求区在上下分栏时高度有限、左右分栏时宽度有限；单一滚动容器在两种布局下都更稳定，也不会额外增加一排导航按钮。

##### smart-doc 参考与取舍

本次参考 smart-doc 的公开 UI 与生成文档页面，借鉴其信息组织方式，不把它当作 Apogee 的视觉模板：

- [smart-doc 主仓库](https://github.com/smart-doc-group/smart-doc)
- [smart-doc-ui 仓库](https://github.com/smart-doc-group/smart-doc-ui)
- [Smart-Doc 官方站点](https://smart-doc-group.github.io/)
- [smart-doc-demo 生成文档页面](https://raw.githubusercontent.com/shalousun/smart-doc-demo/master/src/main/resources/static/doc/index.html)

可借鉴的部分是 endpoint 摘要元信息、接口分组意识、参数定义表，以及 Body/Response 字段树的层级表达。它们帮助开发者按「接口摘要 → 参数定义 → 结构化字段」的顺序阅读；在 Apogee 中，集合、文件夹和请求本身已经提供了分组上下文，因此不再新增一套文档目录。

不直接照搬 smart-doc 的顶部 AppBar、固定左侧 Drawer、独立接口导航、可编辑 Value 输入框、请求/响应示例、cURL 示例和 Send Request 按钮。当前功能是嵌入请求主面板的只读投影：保留 Apogee 的工具栏、分栏和滚动行为，只采用 smart-doc 对信息层级的组织经验；参数值、请求体原文和凭据仍按本节的脱敏规则排除。以下内容是基于公开资料的归纳改写，不是对原页面的复制。

```text
┌──────────────────────────────────────────────────────────────┐
│ GET  用户详情                         接口说明 · 只读 · 未保存 │
│ {{baseUrl}}/users/:id?expand={{expand}}              [复制地址] │
├──────────────────────────────────────────────────────────────┤
│ Path 参数 · 1                                               │
│ 参数名      类型          说明                      状态     │
│ id          string        用户 ID                   已启用   │
├──────────────────────────────────────────────────────────────┤
│ Query 参数 · 2                                              │
│ expand      string        展开字段                  已启用   │
│ page        string        页码                      未启用   │
├──────────────────────────────────────────────────────────────┤
│ Headers · 2                                                 │
│ Accept      string        响应格式                  已启用   │
│ X-Api-Key   string        敏感凭据，不展示值          已启用   │
├──────────────────────────────────────────────────────────────┤
│ Body 参数 · JSON                                            │
│ 参数                  类型          说明                    │
│ profile               object        未提供参数说明          │
│   id                  number        未提供参数说明          │
│   name                string        未提供参数说明          │
├──────────────────────────────────────────────────────────────┤
│ 鉴权  Bearer Token · 不展示凭据                              │
│ 请求设置  展示字段定义，不展示配置值                        │
└──────────────────────────────────────────────────────────────┘
```

信息顺序固定为：

1. **请求摘要**：方法、请求名称、接口地址模板、只读状态、未保存状态。地址只保留路径和参数名；普通 Query 的实际值不展示，非敏感变量占位符可保留。
2. **Path 参数**：参数名、类型、说明、启用状态；不展示当前值，也不虚构 required。
3. **Query 参数**：参数名、类型、说明、启用状态；不展示当前值，也不虚构 schema。
4. **Headers**：只展示请求显式配置的 Header 名称、类型和说明；自动生成的协议 Header 不伪装成接口定义。
5. **Body 参数**：优先展示参数树。JSON 根据当前结构推断 object、array、string、number、boolean、null 等类型，并按层级展示字段说明；form-data/urlencoded 展示平面参数树；raw、binary 只展示类型能力，不输出原文或路径。
6. **鉴权**：展示鉴权字段定义、参数位置和凭据类型，不展示用户名、Token、API Key 或密码值。
7. **请求设置**：只列出请求级覆盖字段的名称、类型和作用，不展示具体配置值。

参数说明优先读取已有字段说明；JSON Body 当前模型没有字段级说明时显示「未提供参数说明」。当前数据模型没有 required、schema、响应定义等信息，文档不得根据一次请求值或响应猜测这些内容。

#### 4.2.4 现有数据到文档 UI 的映射

| 数据源 | 文档呈现 | 规则 |
| --- | --- | --- |
| 请求标签名称、`RequestSpec.method/url` | 摘要标题、方法徽标、接口地址模板 | 去除 URL userinfo 和 Query 实际值；若 `pathParams` 记录了路径实际值，则按参数名替换为 `{name}`；保留路径、参数名和非敏感变量占位符；复制内容与页面一致 |
| `pathParams/params/headers: KeyValue[]` | 参数定义表 | 展示参数名、类型、说明、状态；不展示 `value`，不推断 required/schema；`kind=file` 显示 `file`，其他当前字段显示 `string` |
| `Body.json` | Body 参数树 | 解析 JSON 结构后递归展示字段名、层级和结构类型；不渲染 JSON 原文或任何字段值；字段说明缺失时显示「未提供参数说明」；JSON 无效时显示无法生成参数树的提示 |
| `Body.formData/urlEncoded` | Body 参数树 | 展示字段名、`string/file` 类型、配置中的 description 和启用状态；不展示字段值 |
| `Body.text` | Body 类型说明 | 只展示 raw/content type 及「无法推导结构化参数树」提示，不展示原始 Body |
| `Body.binary` | Body 类型说明 | 只展示 binary/本地文件引用能力，不展示文件名、路径或文件内容 |
| `Body.graphQl` | GraphQL 类型说明 + Variables 参数树 | 不展示 Query 文本；Variables 为合法 JSON 时按参数树展示结构和类型，不展示变量值 |
| `AuthConfig` | 鉴权字段定义表/摘要 | 展示字段名、类型、位置和说明；Basic 密码、Bearer Token、API Key 值永不进入文档 ViewModel |
| `RequestSettings` | 请求设置字段定义表 | 仅显示显式覆盖字段的名称、抽象类型和作用，不展示具体配置值 |

首版仍不展示端点说明、标签/弃用状态、请求/响应 Schema、按状态码定义的响应和持久化 Example。当前持久模型没有这些字段，UI 不得根据一次响应或当前值猜测。JSON Body 的类型树是对当前内存内容的结构推断，不等同于持久化 Schema；若后续需要完整 API 文档，必须先扩展 Rust 模型、YAML、IPC/生成类型和导入映射，再扩展本视图。

首版也不把 `ActualRequest`、最近一次响应或请求体原文混入文档：它们包含环境解析后的 URL、Header、Cookie、Token 或实际数据，并且会随一次发送变化。实际请求仍留在响应区「实际请求」Tab，文档只描述当前请求的接口结构。

#### 4.2.5 脱敏规则

文档态更适合展示和截图，因此安全边界比编辑态更严格：

- 参数表和 Body 参数树永远不渲染 `KeyValue.value`、JSON 字面量、raw 文本、GraphQL Query 或 Variables 值；`KeyValue.kind === 'secret'` 只影响字段说明和安全标记，不产生掩码值列。
- Basic password、Bearer token、API Key value 只展示字段定义；API Key 只展示参数名称与 header/query/cookie 位置。
- Header 名称匹配 `authorization`、`proxy-authorization`、`cookie`、`set-cookie`、`x-api-key` 等敏感集合时，只展示 Header 名称、`string` 类型和脱敏说明。
- URL userinfo 被移除；URL Query 实际值全部省略，只有非敏感变量占位符（如 `{{page}}`）可保留；若 `pathParams` 中记录了路径参数的当前值，文档会将完整路径段替换为 `{name}`，避免把字面量 id 带入页面；文档的「复制地址」复制同一份接口模板。
- 不提供参数值或 Body 内容复制按钮，不通过 `title`、Tooltip、ARIA label 或 DOM attribute 暗藏原值。
- 变量只展示 `{{name}}` 占位符，不解析密钥变量。文档投影不得读取当前环境的 secret value。

#### 4.2.6 组件边界与复用

| 组件/模块 | 建议位置 | 责任 | 当前状态 / 复用判断 |
| --- | --- | --- | --- |
| `RequestDocumentation.vue` | `components/request/` | 接收已脱敏的 `RequestDocViewModel`，组合摘要、参数定义表、Body 参数树和类型说明，不持有编辑状态或完整 `Tab` | **已实现**；请求域组件，不放进通用 `App*` 包装层 |
| `buildRequestDocumentation()` + `RequestDocViewModel` | `features/requestDocumentation.ts` | 把 Tab/RequestSpec 投影成不含请求值、可直接渲染的数据 | **已实现**；纯函数，未来可供安全导出复用；首版无需新 IPC |
| 参数定义表 | `components/common/`（后续候选） | 展示参数名、类型、说明、状态 | 当前先内置于 `RequestDocumentation`；待 ResponsePanel 出现同一语义的第二个消费者后再抽取 |
| Body 参数树 | `components/common/`（后续候选） | 展示层级、字段名、结构类型和说明 | 当前由 `RequestDocumentation` 轻量渲染；只有其他结构化数据页面复用时再抽取 |
| `EmptyState.vue` | `components/common/`（后续候选） | 无数据标题、说明和可选动作槽 | 本功能使用文档内紧凑空状态，不为单一场景提前新增通用组件 |
| 方法徽标 | `components/http/`（候选） | 统一方法文字和语义色 | 先盘点现有 method pill API；确认两处以上行为一致后再抽，不为本功能强行重构 |

以下内容**不复用**：

- `ParameterEditor` 包含草稿新增行、复选、删除、拖拽和输入事件；把它改成 `readonly` 会留下大量不可用语义，文档应使用独立只读表。
- ResponsePanel 的「实际请求」绑定解析后的 `ActualRequest`，不能整体搬来展示模板文档；只抽取表格、代码块等无数据语义的展示原语。
- 模式控件首版保持 RequestPanel 内的轻量原生按钮组。ResponsePanel 的 Body 视图和 cURL 平台选择属于 Tab/选项选择语义，不仅因为外观相似就提前抽一个万能 Segmented 组件。
- 文档小节容器先保留在 `RequestDocumentation` 内；只有出现第二种结构化文档页面后再抽，避免产生只包一层标题的空壳组件。

#### 4.2.7 实施顺序与验收

实施分三步，避免把新功能与响应区重构绑在一次变更里：

1. **模式壳与状态**：在 RequestPanel 增加固定入口和按 Tab 的会话态，只切换请求主面板。
2. **安全投影与文档 UI**：先实现纯数据投影/脱敏，再渲染 `RequestDocumentation`；所有类型分支都消费 ViewModel，不在模板中临时判断密钥。
3. **公共展示原语**：文档功能稳定后，再单独把 ResponsePanel 的重复只读表格、代码块和空状态迁到 common 组件，逐项做视觉回归。

实现完成需满足：

- 从任一编辑 Tab 一次点击进入文档，一次点击返回；模式控件不跳位。
- 只替换请求主面板，URL 栏、响应区、分栏比例和请求内容不被重置。
- 每个请求 Tab 独立记忆模式；关闭后清理，切换模式不产生未保存标记。
- 文档实时反映当前内存配置和启用状态，但自身不存在任何修改入口；参数表和 Body 参数树不展示请求示例值。
- 页面和复制内容中都找不到可识别的鉴权、Cookie、API Key 或 secret 原值，也不包含请求体原文。
- JSON Body 仅可根据当前结构推断基础类型和层级；无模型字段时不显示虚构的 required、schema、响应说明或字段描述。
- 上下分栏和窄的左右分栏都只有一个主体滚动容器；参数说明长文本可换行，Body 参数树按层级缩进，不能为展示示例值而增加代码块。
- 键盘可切换模式，焦点指示清晰；读屏能识别当前模式和「只读」。
- 重新核算主界面可点击元素预算（§1 的同时可见 ≤40）；若超预算，优先收敛当前 Tab 的低频动作，不隐藏模式入口。

### 4.4 响应区 —— 性能设计的核心战场

```
● 200 OK  ·  142 ms  ·  4.2 KB  ·  HTTP/2       [树] [原文] [表格] [预览] [⧉] [↓]
Body   Headers(12)   Cookies(2)   Timing   Console(3)
┌──────────────────────────────────────────────────────────────────────────┐
│ ▾ {                                                    🔍 过滤 JSONPath  │
│     "code": 0,                                                           │
│   ▾ "data": {                                                            │
│       "id": 1024,                                                        │
│       "name": "张三",                                                    │
│     ▸ "roles": [ 3 items ]                                               │
│     }                                                                    │
│   }                                                                      │
└──────────────────────────────────────────────────────────────────────────┘
```

四种视图：

| 视图 | 用途 | 大数据策略 |
| --- | --- | --- |
| **树视图**（默认，JSON/XML） | 结构浏览、折叠、路径复制 | 虚拟滚动，只渲染可视节点；节点数据由 Rust 侧按需分页提供 |
| **原文视图** | 看原始字节、正则搜索 | CodeMirror 6 大文档模式 + 按 range 分段加载（阈值见下方分级表） |
| **表格视图** | 数组型响应（列表接口）→ 转成表格 | 虚拟滚动表格 |
| **预览视图** | HTML / 图片 / PDF / SVG | 沙箱 iframe，禁网络请求 |

**分级降级策略**（这是不卡的关键）：

| 响应体大小 | 树视图 | 原文视图 | 建索引的内存代价 | 其它 |
| --- | --- | --- | --- | --- |
| < 512 KB | 全功能：高亮 + 折叠 + 搜索 | 全量高亮 | < 5 MB | — |
| 512 KB ～ 2 MB | 虚拟滚动，按需分页取节点 | 视口内高亮（延迟计算） | ≈ 5～18 MB | — |
| 2 MB ～ 50 MB | 需手动点「解析」，解析后虚拟滚动 | **关闭语法高亮**，只保留行号 | ≈ 18～455 MB ⚠️ | 提供「只看前 1000 行」 |
| > 50 MB | **不可用** | 不可用 | 会超 900 MB，禁止 | 只显示摘要 + 「保存到文件」/「用外部编辑器打开」/「流式预览头部」 |

**唯一的高亮阈值是 2 MB**，三份文档统一按此口径。

**内存代价一列是 Spike S2 实测外推的**（见 `spikes/results/s2-report.md`）：当前实现下建 JSON 索引的内存开销稳定在响应体体积的 **9.1 倍**（实测 1MB→9.0MB、10MB→91.3MB）。这决定了两件事：

1. **「> 50 MB 树视图不可用」是内存硬约束，不是 UX 偏好。** 首轮 Spike 无视分级对 100MB 强行建索引，Rust 进程私有内存冲到 1.4 GB 且长时间无响应，直接击穿 PRD §5.1 的内存预算。
2. **「2 MB ～ 50 MB 需手动点解析」也不是为了少点一下。** 50MB 响应体建索引要约 455MB，必须由用户显式触发并承担代价，不能自动做。

> 9.1 倍这个膨胀比本身是当前实现的缺陷（索引实际存的是完整 `serde_json::Value` 树），[03 文档 §4.3](./03-技术架构与数据模型.md) 已记录修正方案：索引改为只存字节偏移。改完之后本表的内存列需要重新实测更新，分级阈值也可以相应放宽。

其它设计点：

- **JSONPath / 过滤框**：右上角常驻，输入 `$.data.roles[*].name` 实时过滤
- **右键节点**：复制值 / 复制路径 / 复制为 TS 类型 / **提取为变量**（一步把 token 写进环境变量，这是高频操作）
- **Timing 瀑布图**：DNS → TCP → TLS → 请求发送 → TTFB → 内容下载，每段带毫秒数
- **状态语义色**：2xx 绿、3xx 蓝、4xx 橙、5xx 红、网络错误深红 + 图标区分

## 5. 关键流程设计

### 5.1 首次启动引导

不做多步向导，只做一屏三选一：

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│                     Apogee                               │
│              打开就能发请求                              │
│                                                          │
│   ┌────────────────┐  ┌────────────────┐  ┌───────────┐  │

│   │ Postman/Swagger│  │  Ctrl+V 即可   │  │           │  │

│                                                          │

└──────────────────────────────────────────────────────────┘
```

选完立刻进主界面并聚焦 URL 栏。**不要求注册、不要求邮箱、不弹产品介绍。**

**设计要点**：原稿这里放的是一个「☐ 我知道数据存在本地，不会上传」的勾选框，现在去掉了。理由有两条 ——

1. 让用户勾一个确认框，本质是把举证责任推给用户，而且多一步阻塞。
2. 源码以 MIT 公开能让用户审阅实现，但一次源码审阅不能自动证明某个二进制发布物的网络行为。因此不该要求用户先勾选相信我们，而应该**直接给出可核对的东西**：数据目录路径当场可见，旁边挂一个「网络行为说明」链接，点开是应用会访问哪些域名、什么时候、为什么；用户还可用抓包工具、Release 校验和、SBOM 和签名自行核对。

这是 [PRD §9.3](./01-产品设计文档.md) 信任对冲策略在界面上的第一个落点。同一份说明也放在「设置 → 关于」里常驻可查。

### 5.2 从 Postman 迁移

**入口设计**：一个入口吃下所有 Postman 导出物（对应 PRD §6.3 决策 D3）。用户不需要知道自己手里的是 collection、environment、globals 还是 Data Dump —— **拖进来，我们自己分类。**

```
拖入文件 / 目录 / Data Dump 压缩包（支持多选混合）
  ↓ 按内容特征识别每个文件的类型与格式版本（不看文件名）
解析预览：
  ┌────────────────────────────────────────────────────┐
  │ 识别到 4 个 Postman 文件                           │
  │ ────────────────────────────────────────────────── │
  │ 📦 用户服务.postman_collection.json                │
  │    格式 v2.1.0 (draft-07)  ✓ schema 校验通过       │
  │    ✅ 请求        128 个                           │
  │    ✅ 文件夹       14 个                           │
  │    ⚠️ 脚本         31 个（28 个可自动转换）        │
  │       └ 3 个用到不支持的 pm API，将标注 TODO       │
  │    ⚠️ 鉴权         OAuth2 需重新授权               │
  │                                                    │
  │ 🌍 dev.postman_environment.json      42 个变量     │
  │ 🌐 globals.json                       8 个变量     │
  │ 🔐 vault-secrets.json（已加密）                    │
  │    └ 需要口令解密：[            ]                  │
  │                                                    │
  │ ❌ 跳过：Monitor / Mock / Flows（平台能力，不支持）│
  │ ────────────────────────────────────────────────── │
  │ 导入到：[新集合: 用户服务 ▾]                       │
  │ ☑ 密钥写入系统钥匙串，不落磁盘明文                 │
  │              [查看详细报告]  [取消]  [导入]        │
  └────────────────────────────────────────────────────┘
  ↓
导入完成 → 生成《迁移报告.md》放在集合目录里，列出所有需要人工处理的点
```

设计要点：

- **格式版本可见**：预览里显式显示识别到的格式版本与 schema 校验结果，让用户知道我们认得他手里的东西。v2.0 / v1 旧格式自动升级，并在报告里说明升级动作
- **Vault 密钥单独处理**：加密格式当场要口令；导入后一律进系统钥匙串，磁盘上只留 `keyring://` 引用
- **校验失败不拒绝导入**：schema 校验不通过时降级为警告继续解析（真实导出文件与官方 schema 并非总是严格吻合），警告写进报告
- **核心设计原则：绝不静默丢弃。** 任何无法转换的内容都要在结果里可见，并保留原始片段作为注释。这是迁移成功率 > 90% 目标的落地方式

### 5.3 发送请求的完整反馈链

```
Ctrl+Enter
  ↓ 0ms      按钮变「取消」，状态栏出现进度条
  ↓ <5ms     变量解析完成（若有未定义变量 → 立即行内报错，不发请求）
  ↓ 网络中   实时显示已用时间、已接收字节数（大响应体尤其重要）
  ↓ 完成     响应区渲染 + 状态行动画（绿色一闪）
  ↓ 后置     脚本执行 → 断言结果条 → 提取的变量在环境面板闪烁提示
```

- **可取消**：请求进行中 `Esc` 或点「取消」立即中止（Rust 侧 abort）
- **失败区分**：DNS 失败 / 连接被拒 / TLS 错误 / 超时 / 证书问题，各自给出**可操作的**提示，例如：
  ```
  ⚠ TLS 证书校验失败：自签名证书
    • 这个域名用的是自签证书，常见于测试环境
    • [为本集合关闭 TLS 校验]（不安全）  [导入 CA 证书]  [查看证书详情]
  ```
  错误信息带「下一步做什么」，是这类工具最容易做出差异的地方。

### 5.4 变量解析可视化

调试时最费时间的是「这个变量到底是什么值」。设计三个入口：

1. **hover 预览**：鼠标停在 `{{token}}` 上，浮层显示 `值 / 来源层级 / 是否密钥`
2. **实际请求预览**（`Ctrl+Shift+P`）：显示变量替换后即将发出的原始 HTTP 报文
   ```
   POST /login HTTP/1.1
   Host: api.dev
   Authorization: Bearer eyJhbGc••••（密钥已打码）
   Content-Type: application/json

   {"user":"admin"}
   ```
3. **未定义变量拦截**：发送前校验，未定义的变量红色下划线 + 一键「创建到当前环境」

## 7. 视觉设计规范

### 7.1 设计语言

克制、密集、低对比装饰、高对比内容。信息密度参照 VS Code 与 Linear。

**内容区之间用「块 + 间隙」分隔，不用 1px 细线。** 层级读起来是「壳 → 画布 → 块」：顶栏与状态栏是通栏贴边的装饰（`--a-bg-2`），中间是画布（`--a-bg-1`），侧边栏 / 请求头 / 请求体 / 响应各是一个 6px 圆角块浮在画布上，块与块之间隔 3px（`--a-gutter`）。区域靠底色差划分，不靠描边。

`--a-gutter` 刻意不挂到 §7.3 那条 4px 间距栅格上：栅格管的是内容的排版节奏（padding、行距），而这里是**分隔尺寸**，和边框粗细同类。加上两侧块各自 1px 边框，实际视觉分隔是 5px。圆角用 6px 而不是 10px 也是间隙决定的 —— 间隙只有 3px 时，两块相接处若各带 10px 圆角，会在边缘留出一个约 10px 的缺口，看着像块被掐了一下。

这与「不做 Postman 式卡片化」不冲突，区别在粒度：

- **卡片化**是给每一条内容套卡片 —— 列表项、参数行各自带边框和内边距。那会摊薄信息密度，是被排除的方向。
- **块状分隔**只作用在**顶层区域**之间。块内部仍然是 28px 行高的密集表格，参数行、集合树项都没有独立边框。

代价是可量的：垂直方向 4 条间隙 × 3px = 12px，水平 3 条 × 3px = 9px。1280×820 窗口下内容高度从 760px 降到 748px，少 **1.6%**。这笔支出买到的是区域边界不再依赖一条 1px 低对比细线 —— 那条线在暗色主题下本来就接近不可见（`--a-border` 对 `--a-bg-2` 只有 1.20:1）。

实现是 `tokens.css` 里的 `.a-block` 一个类，布局组合在 `AppBody.vue`。有个坑记在这里：`.a-block` 带 `overflow: hidden`（让内容被圆角裁掉），但**含弹层的块必须覆盖它** —— 请求头块只有 74px 高，URL 栏方法选择器的下拉有 110px+，裁掉就等于菜单打不开。那个块改成 `overflow: visible` 并把圆角传给首尾子元素。

配色采用 **Apogee 深空色系**：冷调中性色阶（不用纯黑、不用中性灰，全部向蓝倾斜）+ 冰蓝强调色。这套色系解决了原配色的一个实际问题 —— 原来的 `#1A1A1C` / `#33333A` 是纯中性灰，在暗环境下层级之间几乎分不开。带色相倾向的色阶让 5 层背景在同样的亮度差下更容易区分。

**唯一的实现来源是 `src/styles/tokens.css`。** 下面的表是它的摘要，不是第二份定义。`src/theme.ts`（naive-ui 主题覆写）必须与令牌一致 —— 这条由 `pnpm check:contrast` 守着，不一致直接 fail。

### 7.2 颜色（暗色为主设计基准）

| 用途 | 令牌 | 暗色 | 亮色 |
| --- | --- | --- | --- |
| 背景 L1（内容区） | `--a-bg-1` | `#0C0E12` | `#F8FAFB` |
| 背景 L2（顶栏/标签栏/状态栏） | `--a-bg-2` | `#14171F` | `#FFFFFF` |
| 背景 L3（输入/抬升面） | `--a-bg-3` | `#1A1E29` | `#F1F4F7` |
| 边框 | `--a-border` | `#232733` | `#DBE2EA` |
| 主文本 | `--a-text` | `#F1F5F9` | `#0F172A` |
| 次文本 | `--a-text-soft` | `#CBD5E1` | `#334155` |
| 弱化文本 | `--a-text-dim` | `#94A3B8` | `#475569` |
| 最弱文本 | `--a-text-faint` | `#7A8AA0` | `#5E6C80` |
| 装饰分隔（豁免对比度） | `--a-text-ghost` | `#3F4A5E` | `#C2CCD9` |
| 品牌主色 | `--a-primary` | `#4F80FF` | `#2563EB` |
| 主色块上的前景 | `--a-on-primary` | `#0C0E12` | `#FFFFFF` |

**注意暗色与亮色的层级方向是相反的，这是有意的。** 暗色下 L1 最深（内容沉下去、装饰浮起来）；亮色下 L1 是云母白而 L2 是纯白（避免大面积纯白刺眼，同时让装饰条浮起来）。

HTTP 方法与状态色。每个语义两个令牌：前景色 `--a-{name}` 与 pill 底色 `--a-{name}-bg`。

| 语义 | 令牌 | 暗色前景 | 亮色前景 | 附加通道 |
| --- | --- | --- | --- | --- |
| GET / 2xx 成功 | `--a-get` / `--a-ok` | `#6EE7B7` | `#047857` | 文字 + `●` |
| POST / 3xx 重定向 | `--a-post` / `--a-redirect` | `#7DD3FC` | `#0369A1` | 文字（3xx 加 `↻`） |
| PUT / 4xx 客户端错误 | `--a-put` / `--a-warn` | `#FCD34D` | `#B45309` | 文字（4xx 加 `▲`） |
| PATCH | `--a-patch` | `#D8B4FE` | `#7E22CE` | 文字 |
| DELETE / 5xx | `--a-delete` / `--a-error` | `#FCA5A5` | `#B91C1C` | 文字 + `▲` |
| HEAD / OPTIONS | `--a-head` | `#94A3B8` | `#475569` | 文字 |
| 网络错误 | `--a-neterr` | `#FFE4E6` on `#9F1239` | `#FFF1F2` on `#9F1239` | **实色填充** + `▲` |

网络错误刻意用**实色填充**而不是换色相：rose 与 red 在半透明 pill 里几乎分不开，靠「填充 vs 半透明」的份量差 + 图标区分更可靠。

所有正文对比度 ≥ 4.5:1，符合 WCAG 2.1 AA。**这条以前只是一句声明，现在是可执行的门禁**：`pnpm check:contrast` 解析 `tokens.css` 与 `theme.ts`，跑 88 项对比度检查（含 pill 合成底色、渐变两端、焦点指示器的 WCAG 1.4.11 3:1、叠加层可感知度）+ 28 项两文件色值一致性检查，任一不达标即 fail。

引入门禁时实测发现的问题（都已修）：

- 原配色的 `--x-text-faint` 暗色只有 **3.18:1**、亮色 **2.84:1**，「≥4.5:1」这句声明本身不成立。
- Apogee 规范原值也有三处不达标：`dim` 文字亮色 **2.35:1**；主按钮白字压在 `#4F80FF` 上 **3.58:1**、压在渐变末端 `#38BDF8` 上 **2.14:1**（按钮右半边的字不可读）；焦点环 `rgba(...,.07)` 只有 **1.08:1**，最大通道差 16 级，基本不可见。
- 修法：暗主题主按钮改用**深色前景**（`--a-on-primary`），保住冰蓝的穿透力；亮主题渐变末端从 `#0EA5E9` 压深到 `#0E7CAE`（白字 4.65:1），代价是天蓝略钝，换「发送」这个最重要的按钮全幅可读；焦点环回到实色 `outline`。

### 7.3 字体与间距

- UI 字体：`Inter` / 系统默认（Windows: Segoe UI，macOS: SF Pro）+ 中文回退 `PingFang SC` / `Microsoft YaHei UI`。**不下载字体文件** —— 装了就用，没装回落系统字体，首屏不为字体付网络或体积代价。
- 等宽字体：`JetBrains Mono` / `Cascadia Code` / `SF Mono`，用于所有代码与 URL
- 字号：UI 13px，代码 13px，次要说明 12px，最小 11px，标题 15px。**固定 px，不用 `clamp()`**
- 行高：UI 20px，代码 20px
- 间距栅格：4px 基数（4 / 8 / 12 / 16 / 20 / 24 / 32 / 40）
- 圆角：4px（徽章/小控件）/ 6px（输入、按钮、内容块）/ 10px（模态、命令面板）/ 胶囊（仅方法与状态徽章）
- 表格行高 28px，紧凑模式 24px（设置可切换）

**为什么不用 Apogee 规范里的流体字号**：它给的是 `clamp(13px, 0.875rem, 14px)` 这类写法，但 `rem` 不随视口变化，所以这个 `clamp` 永远解析成同一个值 —— 实测 base 恒为 14px、`sm` 12px、`lg` 16px。既没有流体效果，又把这里定的 13px 悄悄改成 14px，破坏 20px 行高与 28px 行高的栅格。桌面应用本来也不该让正文字号跟着窗口缩放。

**为什么圆角比 Apogee 规范小一档**：规范给 6/9/14px + 999px 胶囊按钮。28px 行高配 9px 圆角在密集表格里会显胖，而 999px 胶囊按钮与 §7.1「参照 VS Code 与 Linear 的信息密度」不是一路（Linear 实际用 4～6px）。胶囊只保留给徽章 —— 那是它真正合适的地方。

### 7.4 动效预算

**动效是性能杀手，严格限制**：

- 只保留 4 类动效：面板展开/折叠、Toast 进出、响应完成状态闪烁、加载指示
- 时长 ≤ 150ms，缓动 `cubic-bezier(0.4, 0, 0.2, 1)`
- 只用 `transform` 和 `opacity`，禁止动画 `width`/`height`/`box-shadow`（**静态** `box-shadow` 可以用，阴影分三级见 tokens.css）
- 尊重 `prefers-reduced-motion`，开启时全部关闭
- **禁止**：列表项进入动画、页面切换过渡、骨架屏波纹动画

**从 Apogee 规范里没有采纳的部分**，逐条记录理由，避免以后有人照着规范原文又加回来：

| 规范给的 | 不采纳的理由 |
| --- | --- |
| `--duration-base: .3s`、`--duration-slow: .6s` | 超出本节 ≤150ms 的预算。`tokens.css` 里刻意只提供**一档**时长 `--a-dur`，多一档就会有人拿它写 300ms |
| `--ease-spring`（弹性缓动） | 不在本节允许的 4 类动效内 |
| 「发送」按钮 14 颗粒子径向爆炸 0.6s | 撞 §1 首屏 DOM < 800 节点预算，也撞 §7.4 的时长与属性限制 |
| 星空粒子背景 | 持续动画 + 额外 DOM 节点，且撞 §8「不放插画（省体积）」 |
| hover 时改 `box-shadow` | 本节明文禁止动画 `box-shadow` |
| 毛玻璃 `backdrop-filter`（顶栏/侧边栏半透明） | 大面积 blur 在 Windows WebView2 上的合成开销**未实测**，而侧边栏正是要虚拟滚动 1000+ 请求的热区。需要单开一个 Spike 量过才能决定，不能凭规范直接引入 |

渐变只用在一个元素上：「发送」按钮（`--a-primary-gradient`）。这是 Apogee 规范里「核心视觉焦点」的落点，也是唯一值得付这份代价的地方。

### 7.5 Naive UI 使用约定

Naive UI 是 CSS-in-JS 方案，运行时会注入样式，这是首屏性能的潜在风险点。约定：

1. **按需引入**：`unplugin-vue-components` + `NaiveUiResolver`，不做全量 import
2. **主题静态化**：`themeOverrides` 定义为模块级常量对象，绝不在 `computed` 里重建（否则每次都触发全量样式重算）
3. **`n-config-provider` 只包一层**，放在应用根节点 —— **已由 Spike S5 验证可行，见下**
4. **热路径不用重组件**：集合树、参数表格、响应树这三个高频渲染区域**自研轻量组件**，不用 `n-tree` / `n-data-table`。
   理由要说准 —— **是为了首次渲染时间和 DOM 数量，不是为了滚动更流畅**。Spike S3 用「全量 `v-for` 渲染」做对照组量过：
   5000 行时全量渲染首帧 146.6 ms（已击穿 PRD 的 100 ms 集合树预算，其中 layout 一项就 88.2 ms）、铺 5000 个 DOM 节点；自研虚拟滚动首帧 26.8 ms、只铺 35 个。
   但**两者滚动都是 0% 掉帧** —— 已经布局好的长列表滚动由合成器处理，主线程不参与。所以「组件库的树滚起来会卡」这个直觉是错的，
   真正的问题是它一次性铺出全部 DOM，代价落在首帧和内存上。
5. **优先用 Naive UI 的场景**：表单控件、下拉、模态、Toast、Tooltip、设置页——低频、非热路径
6. 图标用 `@vicons` 按需引入，或直接内联 SVG（更省）
7. **禁止在 vite 里做手动 vendor 分包** —— 这是 S5 最反直觉的一条，见下

**Spike S5 实测结果（已验证）**

用 2×2 矩阵测了「naive-ui 放首屏 / 全懒加载」× 「手动 vendor 分包 / 打包器默认分包」四种组合。首屏定义为：从 entry 出发**只走静态 import 边**可达的全部 JS + CSS（不含 `dynamicImports`）。

| 组合 | 首屏 gzip | 预算占用 | naive-ui 在首屏 | 达标 |
| --- | --- | --- | --- | --- |
| naive-ui 进首屏 + **默认分包** | **101.9 KB** | 68% | 是 | PASS |
| naive-ui 全懒加载 + 默认分包 | 42.3 KB | 28% | 否 | PASS |
| naive-ui 进首屏 + 手动分包 | 163.8 KB | 109% | 是 | **FAIL** |
| naive-ui 全懒加载 + 手动分包 | 144.6 KB | 96% | **是**（懒加载失效） | PASS |

两条结论：

- **第 3 条约定可以保留。** 按文档原样把 `n-config-provider` 放在根节点，首屏 101.9 KB gzip，只用掉 150KB 预算的 68%。naive-ui 进首屏的实际代价是 59.7 KB。
- **分包策略比 naive-ui 放哪更关键。** 手动 vendor 分包会把只被动态 `import()` 用到的 naive-ui **提升为 entry 的静态依赖**，懒加载在产物层面直接失效 —— 同一份代码首屏从 42.3 KB 膨胀到 144.6 KB，3.4 倍。这就是第 7 条的来源：手动分包看起来是优化，实际会破坏动态 import 的边界。仓库里 `vite.config.ts` 已把 `manualChunks` 默认关闭，只保留 `S5_MANUAL_CHUNKS=1` 作为可复现对照。

顺带验证了一条选型判断：CodeMirror 6 在所有组合下都正确落在懒加载 chunk（107 KB gzip 单独一个）。如果当初选了 Monaco，光这一块进首屏就直接击穿预算 —— [03 文档 §1.2](./03-技术架构与数据模型.md) 排除 Monaco 的理由成立。

**CI 门禁**：`node scripts/measure-bundle.mjs`，首屏 gzip 超 150KB 即 fail，同时断言 CodeMirror 不在首屏（后者比体积数字更容易被无意破坏）。

### 7.6 Naive UI 的 Apogee 包装层（App*）

Naive UI 只作为实现基础，不作为业务页面的直接 UI API。为了让后续页面复用统一的 Apogee 风格，项目提供 `src/components/ui/` 包装层，并通过 `src/components/ui/index.ts` 作为稳定入口。

#### 设计目标与边界

- **业务代码依赖 App*，包装层依赖 Naive UI**：`views/` 和普通业务组件默认从 `@/components/ui` 导入，不直接从 `naive-ui` 导入。需要新的 Naive UI 能力时，先扩展现有包装组件或新增一个 `App*` 组件。
- **包装层保持薄**：包装组件只负责 Apogee 默认值、`app-*` 样式钩子和常用 slot/属性透传，不复制业务逻辑、不封装请求状态、不在组件内部创建全局状态。
- **主题只有一个边界**：颜色、字体、圆角和 Naive UI 主题覆写继续由 `src/styles/tokens.css`、`src/theme.ts` 和 `NaiveThemeScope` 管理。`App*` 组件禁止自行创建 `NConfigProvider`，避免嵌套 provider、重复注入样式和破坏 S5 的首屏边界。
- **低频控件优先**：表单、下拉、弹窗、确认、提示、设置页等低频交互使用包装层；集合树、请求编辑表格、响应树/响应 Tab、标题栏窗口控制等首屏或热路径继续使用自研轻量控件，不为了统一 API 强行替换。
- **原生能力仍可覆盖**：包装层默认值可以通过同名 prop 覆盖，Naive UI 的 attrs、事件和组件支持的 slot 应继续可用；包装层不应为了“统一”而隐藏必要能力。

#### 当前组件清单

组件入口为：

```ts

  AppAlert,
  AppButton,
  AppCard,

  AppFormItem,

  AppSelect,
  AppSpace,

```

| 分类 | App* 组件 | Apogee 默认行为 / 主要用途 |
| --- | --- | --- |
| 操作控件 | `AppButton`、`AppDropdown` | 默认 `small`；按钮、低频操作菜单 |
| 表单控件 | `AppForm`、`AppFormItem`、`AppInput`、`AppInputNumber`、`AppSelect`、`AppSwitch` | 表单及控件默认紧凑尺寸；`AppFormItem` 跟随表单尺寸 |
| 容器与布局 | `AppCard`、`AppSpace` | 统一挂载 `app-card` / `app-space` 样式钩子；不改变业务布局语义 |
| 弹层与反馈 | `AppModal`、`AppPopconfirm`、`AppAlert` | `AppAlert`、`AppPopconfirm` 默认不显示图标；用于表单弹窗、危险操作确认和持久错误提示 |
| 标签页 | `AppTabs`、`AppTabPane` | 复用 Naive UI tabs；`AppTabPane` 的 `name` 是必填标识 |
| 状态展示 | `AppTag` | 默认 `small`、`bordered=false`；用于导入状态、轻量状态徽章 |

所有包装组件都保留 `class="app-*"` 样式钩子，并使用 `$attrs` 透传原生属性和事件。slot 只转发 Naive UI 实际支持的 slot：例如 `AppCard` 支持默认内容、`header`、`header-extra`、`action`、`footer`，`AppModal` 支持默认内容、`header`、`footer`、`action`。不要臆造 Naive UI 不存在的 slot 或 slot props。

#### 使用示例

低频表单页面应保持业务语义，不在页面中暴露 Naive UI 组件名：

```vue
<script setup lang="ts">
import {
  AppButton,
  AppForm,
  AppFormItem,
  AppInput,
  AppModal,
} from '@/components/ui'
</script>

<template>
  <AppModal v-model:show="show" preset="card" title="新建请求">
    <AppForm>
      <AppFormItem label="名称">
        <AppInput v-model:value="name" placeholder="请求名称" />
      </AppFormItem>
    </AppForm>
    <template #action>
      <AppButton type="primary" @click="submit">创建</AppButton>
    </template>
  </AppModal>
</template>
```

Tabs 必须显式提供稳定的 pane 标识：

```vue
<AppTabs v-model:value="activeTab">
  <AppTabPane name="params" tab="Params" />
  <AppTabPane name="headers" tab="Headers" />
</AppTabs>
```

#### 已落地的迁移范围

当前已将低频工作区交互迁移到包装层：

- `src/components/sidebar/Sidebar.vue`：工作区新建菜单、工具按钮、删除确认、错误提示等使用 `AppDropdown`、`AppButton`、`AppPopconfirm`、`AppAlert` 等包装组件。
- `src/views/NewModal.vue`：新建流程使用 `AppModal`、`AppForm`、`AppFormItem`、`AppInput`、`AppButton`、`AppTag`、`AppAlert`。
- `src/views/SettingsModal.vue`：设置表单使用对应的 `App*` 控件。

这些迁移不改变 `NaiveThemeScope` 的 provider 边界，也不触碰侧边栏虚拟树、请求编辑器和响应查看器的热路径。

#### 后续新增组件的规则

1. 新 UI 先判断是否属于低频、非大列表、非编辑器场景；符合时从 `@/components/ui` 复用，不直接 import `naive-ui`。
2. 现有包装组件不够用时，优先补充一个薄的 `App*` 包装；组件名与 Naive UI 一一对应，避免把多个业务流程揉成一个“大而全”组件。
3. 默认值只收敛 Apogee 视觉和密度：尺寸、是否显示图标、标签边框等可以统一；颜色、字体、圆角不要在每个包装组件中重复定义，应继续使用 token 和主题 provider。
4. 使用 `defineOptions({ inheritAttrs: false })` 时，要明确把 `$attrs` 传给内部 Naive UI 组件；新增必填 prop（例如 `AppTabPane.name`）必须显式声明并传递，不能依赖 `$attrs` 猜测类型。
5. 只转发目标 Naive UI 组件真实存在且类型允许的 slot。修改 slot 转发后必须运行 `pnpm typecheck`，因为编辑器诊断不一定能暴露 `vue-tsc` 模板类型错误。
6. 提交包装层改动至少验证：`pnpm typecheck`、`pnpm build`、`pnpm check:contrast` 和 `git diff --check`；涉及热路径或 provider 边界时，还要复核 S5 首屏体积和对应 Spike 结果。

## 8. 空状态与错误设计

| 场景 | 设计 |
| --- | --- |
| 无集合 | 「还没有集合」+ 三个按钮：新建 / 导入 / 打开目录。不放插画（省体积） |
| 无历史 | 「发出第一个请求后，这里会记录」 |
| 请求未发送 | 响应区显示快捷键提示：`Ctrl + Enter 发送` |
| 搜索无结果 | 「没找到 `xxx`」+ 建议：检查是否在其他集合 / 清除过滤条件 |
| 网络错误 | 错误类型 + 原因 + **可操作按钮**（见 §5.3） |
| 变量未定义 | 行内红色下划线 + hover「变量 `token` 未定义」+ 一键创建 |
| 响应体过大 | 摘要卡片 + 保存到文件 / 外部打开 / 预览头部 |
| 脚本报错 | Console Tab 显示堆栈 + 行号，点击跳转到脚本对应行 |

错误文案三段式：**发生了什么 → 为什么 → 现在能做什么。** 不出现「未知错误」「操作失败」这类无信息量文案。

## 9. 待验证的交互假设

设计稿不是结论。以下假设需要在 v0.1 用户测试中验证：

1. 「单击预览 / 双击固定」的标签行为是否符合直觉，还是造成困惑
2. 上下分栏 vs 左右分栏，哪个作为默认更合适（可能和屏幕尺寸相关，考虑按窗口宽度自动选择）
3. 「从响应提取变量」的右键入口是否够显眼，是否需要在响应工具栏也放一个
4. 四层组织结构够不够用，会不会有用户抱怨缺少 Example / 多环境组
5. 默认隐藏脚本 Tab（仅在有脚本时显示徽标）会不会导致功能发现不了
