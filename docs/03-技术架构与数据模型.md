## 1. 技术选型

### 1.1 选型总表

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 桌面容器 | **Tauri 2.x** | 使用系统 WebView（Windows: WebView2 / macOS: WKWebView），核心体积远小于打包 Chromium，是达成「安装包 < 15MB」的前提。⚠️ **这条红利只兑现在体积上，不兑现在内存上**：安装包 1.28MB，但 WebView2 运行时仍要 ~147MB 常驻（S1），空闲内存预算因此按实测定在 220MB（S3，见 §4.2）。按决策 D2，Linux/WebKitGTK 不在 v1.0 范围，但不写平台专有代码 |
| 后端语言 | **Rust**（2021/2024 edition） | 无 GC、可控内存、真并发；HTTP 与 JSON 处理放在这里才能保证前端不卡 |
| 异步运行时 | **tokio**（multi-thread） | 生态标准；请求并发与流式处理需要 |
| HTTP 客户端 | **reqwest**（rustls backend） | 成熟、支持 HTTP/2、流式 body、超时/重定向策略可控。用 rustls 而非 OpenSSL，避免跨平台编译地狱 |
| HTTP/3 | `reqwest` + quinn（可选 feature） | v0.3 再开，避免早期增加体积 |
| JSON | **serde_json**（+ 可选 simd-json 做大 body 探测） | 大响应体解析必须在 Rust 侧完成 |
| 本地索引库 | **SQLite**（rusqlite，bundled + WAL + FTS5） | 历史、搜索索引、运行记录；bundled 保证无外部依赖 |
| 密钥存储 | **keyring** crate | 对接 Windows Credential Manager / macOS Keychain（Linux Secret Service 后端保留编译但不验证） |
| 脚本引擎 | **QuickJS**（rquickjs） | 冷启动微秒级、内存 KB 级，对比嵌 Node/deno_core 体积小一个数量级；ES2020 足够跑 Postman 风格脚本。决策 D3 要求对齐最新 `pm.*`，脚本语言只能是 JS |
| 前端框架 | **Vue 3.5+**（`<script setup>` + TS） | 需要 `defineModel`、`useTemplateRef`、响应式性能优化 |
| 构建 | **Vite 6/7** + Rolldown（可用时） | 冷启动 dev server 与产物体积 |
| 状态管理 | **Pinia** | 组合式 API 风格一致 |
| UI 组件 | **Naive UI 2.4x** | 按需引入；仅用于非热路径（见 [02 文档 §7.5](./02-交互与界面设计.md)） |
| 代码编辑器 | **CodeMirror 6** | 比 Monaco 小 ~10 倍，原生支持大文档与虚拟视口。Monaco 明确排除 |
| 虚拟滚动 | 自研（`virtua` 备选） | 集合树 / 参数表 / 响应树三处，需要精确控制 |
| 包管理 | **pnpm** | 磁盘与安装速度 |
| i18n | **vue-i18n**（按语言分包懒加载） | 首屏只加载当前语言 |

### 1.2 明确排除的技术

| 排除项 | 原因 |
| --- | --- |
| Electron | 与产品定位直接冲突 |
| Monaco Editor | 体积 ~5MB，大文档性能不如 CodeMirror 6，会击穿包体预算 |
| Node.js 嵌入式脚本引擎 | 体积 +40MB、内存 +50MB |
| Element Plus / Ant Design Vue（全量） | 体积与热路径性能 |
| Tailwind 全量 | 用 CSS 变量 + 少量原子类即可；避免构建期扫描开销与类名膨胀（可选 UnoCSS 按需） |
| 任何运行时 CSS-in-JS 作为主方案 | 只在 Naive UI 范围内容忍 |
| 云端同步作为核心链路 | 违反本地优先原则 |
| **GPL / AGPL / SSPL 许可的依赖** | 项目采用 MIT 且需要保持二进制再分发义务可审计；默认不引入这些 copyleft 许可证的依赖，任何例外须经维护者和许可评估。许可白名单与 CI 阻断见 [PRD §9.5](./01-产品设计文档.md) |

### 2.2 职责边界（最重要的架构约束）

**规则：任何 O(响应体大小) 或 O(集合规模) 的计算都必须在 Rust 侧完成。**

| 工作 | 放在哪 | 说明 |
| --- | --- | --- |
| HTTP 请求执行 | Rust | 前端只发一个命令 |
| 变量解析与替换 | Rust | 保证脚本与请求看到的是同一份解析结果 |
| JSON 解析 / 格式化 / JSONPath 查询 | Rust | 前端拿不到完整 JSON 对象，只拿视口内的节点 |
| 响应体存储 | Rust（磁盘 spool） | 大 body 从不整体过 IPC |
| 语法高亮 | 前端（CodeMirror） | 只对视口内文本高亮 |
| 集合文件读写 / 解析 | Rust | 前端拿到的是扁平化的树节点数组 |
| 搜索 | Rust（SQLite FTS5） | 输入到结果 < 30ms |
| 脚本执行 | Rust（QuickJS） | 沙箱隔离，不占 WebView 主线程 |
| 导入解析（Postman/OpenAPI） | Rust | 大文件不阻塞 UI |
| 布局 / 动画 / 表单交互 | 前端 | — |

## 3. IPC 契约设计

### 3.1 三条通道

| 通道 | 用途 | 数据量 |
| --- | --- | --- |
| `invoke` 命令 | 请求/响应式操作 | 小（< 64KB JSON） |
| 事件 `emit` | 进度、流式消息、文件变更通知 | 小，高频 |
| 自定义协议 `apogee://` | 大响应体、文件内容读取 | 大（MB～GB），WebView 直接按 range 拉取，不经 JSON 序列化 |

**关键决策**：Tauri 的 `invoke` 走 JSON 序列化，10MB 响应体走一次 `invoke` 意味着「Rust 序列化 → 字符串传输 → JS 解析」三次全量拷贝，这正是竞品卡顿的同类问题。所以大数据一律走自定义协议 + HTTP Range 语义。

### 3.2 核心命令清单

```rust
// 请求执行
send_request(req: RequestSpec, ctx: ExecContext) -> ExecHandle   // 立即返回句柄
cancel_request(handle: ExecHandle) -> ()
// 执行进度通过事件推送：request:progress / request:done / request:error

// 响应读取（大数据走协议，不走这里）
get_response_meta(response_id) -> ResponseMeta      // 状态、头、大小、耗时分解
get_response_tree(response_id, path, offset, limit) -> Vec<TreeNode>  // 按需分页取树节点
query_response(response_id, jsonpath) -> QueryResult
// 原文：GET apogee://response/{id}?range=bytes=0-65535

// 集合
list_tree(workspace_id) -> Vec<FlatNode>            // 扁平化，前端自己建索引
read_request(node_id) -> RequestSpec
write_request(node_id, spec) -> ()
move_node(node_id, target_parent, index) -> ()

// 变量
resolve(text: String, ctx: ExecContext) -> ResolveResult  // 含每个变量的来源与是否密钥
preview_raw_request(req, ctx) -> String                   // 预览实际报文（密钥打码）

// 搜索
search(query: SearchQuery) -> Vec<SearchHit>        // FTS5

// 导入导出
analyze_import(path) -> ImportPlan                  // 先出预览与告警，不落盘
apply_import(plan, target) -> ImportReport
export(scope, format) -> PathBuf
```

### 3.3 错误契约

所有命令返回统一错误结构，前端据此渲染 [02 文档 §8](./02-交互与界面设计.md) 的可操作错误：

```rust
struct AppError {
    code: Option<String>,       // 稳定机器码，如 WORKSPACE_SESSION_EXPIRED
    kind: ErrorKind,        // Dns | Connect | Tls | Timeout | Http | Io | Parse | Script | Var
    message: String,        // 已本地化的简述
    detail: Option<String>, // 技术细节（可折叠展示）
    hints: Vec<Hint>,       // 可操作建议，每个带 action id
}
struct Hint { label: String, action: Option<String> } // 如 action: "settings.tls.disable_for_collection"
```

## 4. 性能实现策略

逐条对应 [PRD §5](./01-产品设计文档.md) 的指标。

### 4.1 冷启动 < 800ms

| 手段 | 说明 |
| --- | --- |
| 分阶段启动 | 第一阶段只渲染「顶栏 + URL 栏 + 空响应区」并聚焦输入框；侧边栏、历史、设置异步挂载 |
| 不在启动时读集合内容 | 只读 `.apogee/manifest` 里的树结构索引（Rust 侧维护，含 mtime 校验），集合文件按需读 |
| 前端产物拆包 | 首屏 chunk 目标 < 150KB (gzip)；CodeMirror、图表、设置页、导入器全部动态 import |
| Rust 侧延迟初始化 | SQLite 连接、脚本引擎、文件监听在首次使用时才创建 |
| 窗口先显示后填充 | Tauri 窗口配置 `visible: false` → 首帧就绪后 `show()`，避免白屏闪烁 |
| 无启动期网络请求 | 更新检查延后到启动 30 秒后，且可关闭 |

**Spike S1 实测（Windows，20 轮，release 构建）**

| 阶段 | 中位耗时 | 占比 |
| --- | --- | --- |
| 进程创建 → 第一行 JS（Rust 初始化 + WebView2 起 6 个进程 + 加载 HTML/JS） | **506.5 ms** | **86%** |
| 第一行 JS → Vue 挂载完 | 66.4 ms | 11% |
| 挂载完 → 首个空标签就绪 | 0.4 ms | — |
| 就绪 → 首帧上屏（双 rAF） | 14.4 ms | 2% |
| **合计（进程创建 → 首帧就绪）** | **590.3 ms** | 预算 800ms 的 **74%** |

冷启动（本次会话首次拉起）608.5 ms，全部轮次 p95 672.5 ms，跨度 526.2～746.3 ms。分段是各自序列的中位数，相加与合计中位有几毫秒出入，属正常。

**这张表推翻了上面几条手段的收益预期。** 86% 的启动耗时发生在第一行 JS 之前，而那一段完全由 WebView2 决定，是地板不是噪声。含义有三条：

- 「前端产物拆包」已经做到 101.9KB gzip（S5），继续压的边际收益很小 —— 前端总共只占 13%。
- 真正的优化方向是**让 WebView2 更早开始**，而不是让前端更快完成。但这部分能做的很有限，且不在我们手里。
- **不能只用前端 `performance.now()` 衡量启动**：那样只看到 81.2 ms，会系统性低估 **7 倍**。「性能自检」面板（PRD §5.2）必须显示跨进程口径。

⚠️ 热启动实测 p95 **746.3 ms**，未达 PRD 的 < 300 ms。量测机有背景负载，这个数应视为上限，需空闲机器复测。顺带一条量测经验：**刚构建完的二进制前若干轮会被 Defender 首扫拖慢，且起跑 CPU 门禁挡不住**（实测前 11 轮 788～1234 ms、第 12 轮起 553～638 ms，两段起跑 CPU 都通过门禁）。S1 量测台现在会做预热漂移检测并在报告里标出来，详见 §10.3 第 14 条。

### 4.2 空闲内存 < 220MB（Windows）/ 50 标签 < 450MB

**标签虚拟化**是核心机制：

```
标签状态分三级：
  Active（1 个）   → 完整挂载：编辑器实例 + 响应视图
  Warm（最近 3 个）→ 保留 DOM，但编辑器降级为只读快照
  Cold（其余）     → 只保留 Pinia 里的轻量状态对象（< 2KB/标签）
                     响应体在磁盘 spool，不在内存
```

其它手段：
- 响应体**不进内存**：Rust 侧收到即流式写入 `responses/{id}.bin`，内存只留元信息；磁盘缓存按 LRU 限额（默认 500MB，可配置）
- **JSON 索引缓存也必须按 LRU 淘汰**，且标签切到 Cold 状态时主动丢弃其索引。
  这条是 Spike S2 补上的：原文只规定了响应体磁盘缓存要 LRU，漏了索引缓存。
  实测跑完四档量测后 Rust 进程内存停在 105.6 MB 不回落，就是因为索引一直挂在
  `ResponseStore` 里没人释放 —— 单个 10MB 响应的索引就占 91 MB，攒几个就爆预算
- 历史记录只存 SQLite，UI 按视口分页拉取
- Pinia store 里的大对象用 `shallowRef`，避免 Vue 深度响应式代理开销（一个 1 万节点的树做深度 reactive 会产生数万个 Proxy）
- Rust 侧用 `jemalloc`/`mimalloc`（视平台评估），减少长时间运行的碎片增长

**Spike S1 实测（Windows，20 轮，空壳：1 个空标签、无集合、无 SQLite、无脚本引擎）**

口径是**进程树私有工作集**（`Working Set - Private`，等于任务管理器「内存」列），定义见 [PRD §5.1](./01-产品设计文档.md)。

| 进程 | 每轮实例数 | 私有常驻中位（每实例） | 占比 |
| --- | --- | --- | --- |
| `msedgewebview2` gpu-process | 1 | **75.1 MB** | 48% |
| `msedgewebview2` browser | 1 | 35.8 MB | 23% |
| `msedgewebview2` renderer | 1 | 23.4 MB | 15% |
| `msedgewebview2` utility | 2 | 5.0 MB | 6%（两个合计） |
| `apogee.exe`（Rust 宿主） | 1 | **3.71 MB** | **2.4%** |
| `msedgewebview2` crashpad-handler | 1 | 2.05 MB | 1% |
| **合计** | **7** | **155.7 MB**（峰值 171.5 MB） | 预算 220MB 的 **71% / 78%**（地板，非达标证明） |

**Spike S3 实测（Windows，5 轮干净启动，负载：1 工作区 + 3 标签 + 5000 节点集合树）**

这才是 PRD §5.1 声明的量测条件（还多一棵树），S1 那组是地板。同一口径：

| 进程 | 每轮实例数 | 私有常驻（该角色全部实例合计） | 占比 |
| --- | --- | --- | --- |
| `msedgewebview2` gpu-process | 1 | **71.3 MB** | 45% |
| `msedgewebview2` browser | 1 | 37.6 MB | 24% |
| `msedgewebview2` renderer | 1 | 28.1 MB | 18% |
| `msedgewebview2` utility | 2 | 11.3 MB | 7% |
| `apogee.exe`（Rust 宿主） | 1 | **3.8 MB** | **2.4%** |
| `msedgewebview2` crashpad-handler | 1 | 2.05 MB | 1% |
| **合计** | **7** | **158.8 MB** 中位 / 168.6 MB 最差（跨启动波动 9.1%） | 预算 220MB 的 **72% / 77%** |

⚠️ 两张表的聚合方式不同（S1 是每实例跨 20 轮的中位，S3 是该角色全部实例合计），**逐行相减求「每个角色涨了多少」是错的**。能直接比的只有合计行和 Rust 宿主那一行（都是单实例）。

**从空壳到这个负载，进程树中位只涨了 3.1 MB**（155.7 → 158.8），比跨启动波动（9.1%，约 14 MB）还小，峰值甚至互有高低（171.5 vs 168.6）。Rust 宿主几乎没动：3.71 → 3.80 MB。原因见 §4.4：虚拟滚动让 DOM 量与集合规模无关（实渲染恒为 35 行），标签只是轻量状态对象。

**上面那一整节的手段，管的是 Rust 那 2.4%。** 三个推论：

- **预算的分母由 WebView2 定死，所以 Rust 侧每省 1 MB 都直接变成余量。** 这正是 S2 修掉索引 9.1× 膨胀的价值所在 —— 在只有 3.8 MB 基线的进程里，一个 91 MB 的索引是灾难性的。反过来说，Rust 侧任何新增常驻结构都要盯得很紧。这也是为什么 PRD §5.1 单立了一条「Rust 主进程私有常驻 < 20MB」：**那是唯一一条我们真的守得住的内存门禁。**
- **「进程树总量没涨」不能当作「我们没引入内存问题」的证据。** 总量里 97% 的变动与我们的代码无关，而且它自己的跨启动波动就有 14 MB —— 足以把一个几 MB 的真实回归完全盖住。回归要看 Rust 主进程那条门禁，不要看总量。
- **标签虚拟化必须真的卸掉 DOM 和 JS 对象，只把状态挪进 Pinia 不够。** S3 观测到：反复创建销毁大列表之后驻留内存是 208.0 MB 中位 / 246.2 MB 最差，比干净驻留高约 50 MB，且十几秒的观察窗口内不回落（增量几乎全在 `renderer`）。所以「标签转 Cold」的设计目标不能是「内存立刻回到基线」，而是「不再随标签数线性增长」。这也提醒：**性能自检面板报的内存要说明是哪种状态下的**，否则用户会拿一个用过一阵子的会话去对我们宣称的稳态值。

### 4.3 大响应体不卡（10MB < 300ms / 100MB 不崩）

完整链路：

```
网络流
  ↓ tokio stream，边收边写盘（不 buffer 全量）
Rust: 计算元信息（大小、Content-Type、编码探测）
  ↓ emit request:done { response_id, meta }        ← IPC 只传几百字节
前端: 立即渲染状态行（此时已 < 50ms）
  ↓ 根据 size 选择渲染策略（02 文档 §4.4 分级表）
情况 A（< 2MB）   : 请求树节点第 0 页 → get_response_tree(root, 0, 200)，高亮开启
情况 B（2～50MB） : CodeMirror 通过 apogee:// 协议按 range 拉首屏 64KB，高亮关闭
情况 C（> 50MB）  : 只渲染摘要卡片 + 头部流式预览
  ↓ 用户滚动 / 展开节点
按需再取下一页（Rust 侧有已解析的 JSON 索引缓存）
```

关键点：
- **前端永远不持有完整响应字符串**。这一条打破了 Electron 系客户端的根本瓶颈
- 搜索/JSONPath 过滤也在 Rust 侧执行，返回命中位置列表
- 超大文本用 CodeMirror 6 的分段加载，配合 `>2MB 关闭高亮` 的降级规则

**Spike S2 实测结果（已验证）**

| 指标 | 实测 | 预算 |
| --- | --- | --- |
| 10MB JSON 首屏 | **25.3 ms** | < 300 ms（用掉 8%） |
| 100MB 响应体 | 首屏 21.2 ms，进程存活可继续应答 | 不崩溃、可预览 |
| Range 取首屏 64KB | 2.9 ～ 4.4 ms，**四个体积下基本一致** | — |
| 对照：10MB 全量拉进 JS 并拼串 | 128.9 ms（比 Range 慢 **31 倍**） | — |
| DOM 节点数 | 1MB 带高亮 134 个；10MB 以上关高亮 12 个 | — |

「Range 取分片耗时与响应体大小无关」是本文档最核心的性能论点，S2 用 1MB / 10MB / 50MB / 100MB 四档把它验证了：磁盘侧是 seek + 定长读，100MB 文件读 64KB 的成本和 64KB 文件相同。

**⚠️ 需要修正的设计：现在的「JSON 索引」不是索引，是全量内存副本**

原文这里写的是「JSON 解析在 Rust 侧一次完成，结果保存为『路径 → 值/子节点数』的索引结构」。当前实现（`crates/apogee-core/src/response.rs` 的 `JsonIndex`）内部持有的是整棵 `serde_json::Value`，那是**副本不是索引**。S2 实测其内存开销稳定在 body 体积的 **9.1 倍**：

| body | 索引内存 | 倍数 |
| --- | --- | --- |
| 1 MB | 9.0 MB | 9.03× |
| 10 MB | 91.3 MB | 9.13× |
| 100 MB（首轮强行建索引） | 进程冲到 ~1.4 GB | — |

正确做法：**索引只存字节偏移**，即 `path → (start, end)` 的 span 表，取值时按需从磁盘 spool 读该区间。这样索引内存与 body 体积解耦（只与节点数量线性相关，且每个节点是两个 u64 而不是一棵 `Value` 子树）。

排期：**必须在 v0.2 做树视图之前改掉**，否则 PRD §5.1 的内存预算守不住。改完后重跑 S2 并更新 [02 文档 §4.4](./02-交互与界面设计.md) 分级表的内存列。

### 4.4 集合树 1000 请求 < 100ms

- Rust 侧返回**扁平数组** `Vec<FlatNode>`（含 `id / parent_id / depth / name / method / expanded / debug_case_count`），前端不做递归构造；`debug_case_count` 只是 Request 行的摘要，完整 `DebugCase` 定义不进入工作区快照
- 调试用例子项在前端临时投影为同一虚拟列表中的定高扁平行：仅点击 Request 行上的独立箭头时才读取一次 `list_debug_cases(request_id)`，按请求缓存；快照重载时废弃缓存，避免把外部 YAML 改动显示成旧数据
- 自研虚拟滚动：只渲染可视区约 30 行 + 上下缓冲 10 行
- 展开/折叠只改 `visible` 计算，不重建数组
- 节点渲染组件用 `v-memo` 或函数式组件，避免每行都是完整组件实例
- 大数组用 `shallowRef`，不能用 `ref`：20000 节点做深度响应式会产生 20000 个 Proxy（与 §4.2 同一条约束）。代价是改节点内字段后要手动换引用触发 `visible` 重算
- 视口高度是**输入参数，不是常量**：挂载时从真实元素读，并用 `ResizeObserver` 跟随。写死一个默认值会让首次渲染按错误的行数渲染（S3 抓到的实际 bug，见 §10.2）

**Spike S3 实测结果（已验证，门槛全部通过）**

| 指标 | 实测 | 预算 |
| --- | --- | --- |
| 5000 节点首渲（数据就绪 → 像素上屏） | **26.8 ms** | < 100 ms（用掉 27%） |
| 1000 请求集合树首渲 | **26.6 ms** | < 100 ms（PRD §5.1，用掉 27%） |
| 5000 节点滚动掉帧率 | **0.00%** | < 5%（＝「60fps」的可判定口径） |
| 单步滚动主线程成本（1000 / 5000 / 20000） | 1.0 / **0.9** / 0.8 ms | 一帧预算 13.3 ms 的 7%，**余量约 14 倍** |
| 实渲染行数（1000 / 5000 / 20000 节点） | **35 / 35 / 35** | 由视口高度决定，与节点数无关 |
| O(N) 可见性过滤（1040 / 5000 / 20000） | 0.015 / 0.040 / **0.097** ms | 20000 节点占一帧的 0.7% |
| 首渲计算成本 patch（1040 / 5000 / 20000） | 2.8 / 3.3 / 2.6 ms | 噪声范围内持平，不随 N 单调 |
| 展开/折叠计算成本（1040 / 5000 / 20000） | 2.4 / 2.5 / 2.8 ms | 唯一随规模增长的交互路径，仍在一帧内 |
| 超过 50 ms 的动画帧（LoAF，三档合计） | **0 个** | 自研实现全程无长帧 |
| 对照：全量 `v-for` 渲染 5000 行 | patch 22.0 ms + layout 88.2 ms，首帧 **146.6 ms**，1 个长帧 | 已击穿 100ms 预算 |

三条结论会影响后续实现：

1. **上面这套设计成立的原因是「渲染量与节点数无关」，不是「代码写得快」。** 实渲染行数由视口高度定死，随规模增长的只有一趟 O(N) 扫描。这与 §4.3 的「Range 取首屏分片耗时与 body 体积无关」是同一个架构模式。
2. **虚拟化买到的是首渲时间和内存，不是滚动帧率。** 对照组（全量渲染 5000 行）滚动同样 0% 掉帧 —— 已经布局好的长列表滚动由合成器处理，主线程不参与。差距全在首渲：146.6 ms vs 26.8 ms（其中 layout 88.2 ms vs 1.0 ms），DOM 节点 5000 vs 35。[02 文档 §7.5](./02-交互与界面设计.md) 第 4 条把集合树列为「必须自研」的理由应当写成首渲与内存，而不是「滚动更流畅」。
3. **展开/折叠是唯一需要继续盯的路径。** 它走 `all` 换引用 → `visible` 全量重算，是 O(N)。20000 节点下 2.8 ms，仍在一帧之内，所以当前不需要做增量更新；但真实集合突破十万节点时要重新量。
4. **量测这类组件时不要用「首帧」和「fps」当定量指标。** 三档首帧都是 26.6～26.8 ms，那是 2 个 vsync（75 Hz 下 2×13.3 ms）的等待，把差异全盖住了；帧间隔 p50 一律 13.30 ms 同理。要定量必须用不含 vsync 的口径：`patch`（Vue 打完 DOM）、`layout`（强制同步排版）、单步滚动成本。详见 §10.3 第 8 条。

### 4.5 请求发送开销 < 5ms

- 前端点击 → `invoke("send_request")` 立即返回句柄，UI 不等
- 变量解析、URL 构建、Header 合并、鉴权签名全在 Rust 侧同步完成（微秒级）
- 连接池复用（reqwest Client 全局单例，按代理配置分池）
- DNS 缓存 + happy-eyeballs
- 前置脚本用**已预热的 QuickJS 上下文**（复用 runtime，每次请求只建轻量 context）

### 4.6 输入延迟 < 16ms

- 编辑器输入不触发任何跨 IPC 调用；变量解析结果本地缓存，环境变更时才失效
- 自动保存草稿：300ms 防抖 + 异步写盘
- 参数表格用「非受控输入 + 失焦提交」模式，避免每次按键都跑全量响应式更新
- 禁止在 `watch` 里做同步重计算；重逻辑一律 `requestIdleCallback` 或移到 Rust

### 4.7 包体 < 15MB

- Rust: `opt-level = "z"`、`lto = "fat"`、`codegen-units = 1`、`panic = "abort"`、`strip = true`
- 不打包 Chromium（Tauri 天然优势）；Windows 依赖 WebView2 Runtime（Win11 自带，Win10 提供 bootstrapper）
- 前端：按需引入 + 动态 import + 不用图标字体（内联 SVG）+ 不放插画资源
- 语言包、代码生成模板、导入器等按需加载
- CI 里加**包体预算检查**，超限直接 fail

**Spike S1 实测**：`apogee.exe` **3.96 MB**（已 strip），NSIS 安装包 **1.29 MB** —— 只占 15MB 预算的 **9%**，是所有指标里余量最大的一项。两个前提必须守住：① 上面那组 release profile 参数（`opt-level="z"` + `lto="fat"` + `codegen-units=1` + `panic="abort"` + `strip`）；② WebView2 走 `downloadBootstrapper` 不打进安装包 —— 代价是 Win10 无 Runtime 的机器首次安装需要联网，这是已接受的产品决策。门禁已可用：`pnpm spike:s1`。

⚠️ PRD §5.1 的「磁盘占用（安装后）< 50MB」尚未量测：S1 只量了 exe 与安装包体积，未统计安装后目录（还需计入 `EBWebView` 用户数据目录）。

### 5.2 核心类型定义

```rust
// ── 请求 ──────────────────────────────────────────────
struct Request {
    id: Uuid,
    name: String,
    protocol: Protocol,            // Http | GraphQl | WebSocket | Sse | Grpc
    method: String,                // 允许自定义方法
    url: String,                   // 含 {{变量}} 与 :path 参数
    params: Vec<KeyValue>,         // query
    path_params: Vec<KeyValue>,
    headers: Vec<KeyValue>,
    body: Body,
    auth: AuthConfig,              // 含 Inherit 变体
    scripts: Scripts,
    settings: RequestSettings,
    docs: Option<String>,          // Markdown
    sort_order: i32,
}

struct KeyValue {
    enabled: bool,                 // 对应 UI 勾选框
    key: String,
    value: String,
    description: Option<String>,
    kind: ValueKind,               // Text | File | Secret
}

enum Body {
    None,
    Json(String),
    Text { content: String, content_type: String },
    FormData(Vec<KeyValue>),       // kind=File 时 value 为文件路径，流式上传
    UrlEncoded(Vec<KeyValue>),
    Binary { path: PathBuf },
    GraphQl { query: String, variables: String, operation_name: Option<String> },
}

enum AuthConfig {
    Inherit,                       // 默认：继承父级
    None,
    Basic { username: String, password: String },
    Bearer { token: String },
    ApiKey { key: String, value: String, location: ApiKeyIn }, // Header|Query|Cookie
    OAuth2(Box<OAuth2Config>),
    Jwt(Box<JwtConfig>),
    AwsSigV4(Box<AwsConfig>),
    Ref { profile_id: Uuid },      // 引用集合级 AuthProfile
}

struct Scripts {
    pre_request: Option<String>,
    post_response: Option<String>,
    asserts: Vec<Assertion>,       // 可视化无代码断言
    extracts: Vec<Extraction>,     // 变量提取
}

struct Assertion {
    target: AssertTarget,          // StatusCode | ResponseTime | Header(k) | JsonPath(p) | BodyText
    op: AssertOp,                  // Eq | Ne | Gt | Lt | Contains | Matches | Exists | TypeIs
    expected: String,
    enabled: bool,
}

struct Extraction {
    from: ExtractFrom,             // JsonPath(p) | Header(k) | Regex(r) | Cookie(k)
    to: VarTarget,                 // scope: Runtime | Environment | Global
    name: String,
}

struct RequestSettings {
    timeout_ms: Option<u64>,
    follow_redirects: Option<bool>,
    max_redirects: Option<u8>,
    verify_tls: Option<bool>,      // None = 继承
    http_version: Option<HttpVersion>,
    encode_url: Option<bool>,
    send_cookies: Option<bool>,
    proxy: Option<ProxyConfig>,
}
// 全部 Option：None 表示继承上级，实现「集合 → 文件夹 → 请求」三级配置继承

// ── 变量 ──────────────────────────────────────────────
struct Variable {
    enabled: bool,
    key: String,
    value: String,                 // secret=true 时此处为钥匙串引用 keyring://...
    secret: bool,
    description: Option<String>,
}

// 解析优先级（高 → 低）
// Runtime(脚本写入) > Environment > Collection > Global > 动态内置({{$uuid}} 等)
struct ResolveResult {
    value: String,
    trace: Vec<VarTrace>,          // 每个变量的来源，供 UI hover 展示
    undefined: Vec<String>,        // 未定义变量，用于发送前拦截
}

// ── 响应 ──────────────────────────────────────────────
struct ResponseMeta {
    id: Uuid,
    status: u16,
    status_text: String,
    http_version: String,
    headers: Vec<(String, String)>,
    size_bytes: u64,
    body_path: PathBuf,            // 磁盘 spool 位置，前端通过 apogee:// 读取
    content_type: Option<String>,
    charset: Option<String>,
    timing: Timing,
    from_cache: bool,
    truncated: bool,               // 超过上限被截断
}

struct Timing {
    dns_ms: f64, tcp_ms: f64, tls_ms: f64,
    request_ms: f64, ttfb_ms: f64, download_ms: f64, total_ms: f64,
}
```

### 5.3 变量解析规则（明确定义，避免玄学）

1. 解析在 Rust 侧一次性完成，递归深度上限 10（防 `{{a}}` → `{{b}}` → `{{a}}` 死循环）
2. 未定义变量**不静默替换为空串**，而是返回 `undefined` 列表并阻止发送（可在设置中改为警告后继续）
3. 密钥变量在日志、历史快照、导出、预览报文中一律打码
4. 动态变量在**每次求值时**生成新值（`{{$uuid}}` 两次出现是两个不同值），除非用 `{{$uuid:1}}` 形式指定同一实例

### 5.4 调试用例：定义、运行结果与安全边界（v0.1 MVP）

调试用例不复制 Request 节点，也不创建第二套 HTTP 执行链。首版以 `DebugCase` 绑定既有 Request，并保存可执行的未解析请求快照：

```rust
enum DebugCaseType {
    Success,                       // 预期成功场景
    Failure,                       // 预期失败场景
    Exception,                     // 预期异常场景
}

struct DebugCase {
    id: Uuid,
    request_id: Uuid,        // 所属基础 Request，稳定身份，不以 URL 反推
    name: String,
    case_type: DebugCaseType, // 保存时选定的分类；不是 HTTP 断言
    spec: RequestSpec,       // 保存时的完整、未解析参数快照
    created_at_ms: u64,
    updated_at_ms: u64,
}
```

`PersistedRequest` 新增可选 `debugCases: Vec<DebugCase>` 字段，缺失时按空数组读取，且缺失 `caseType` 时以 `Success` 兼容读取，因而旧 YAML 无需迁移。定义与请求同文件，随 Git 审查、复制和删除；运行结果绝不回写这个字段，避免一次发送制造工作区 diff。`workspace_load` 为每个 Request 只投影 `debugCaseCount`，侧栏展开后才读取完整定义并在工作区 store 按请求缓存；完整响应体继续沿用 Rust spool 与 Range 读取，不能内嵌 YAML 或经 IPC 全量传输。

每次从用例执行后，仍创建现有 `HistoryRecord`，仅增加可选 `debugCaseId` 与 `environmentId` 来源字段：`debugCaseId` 让前端按用例找到最近一次结果，`environmentId` 防止测试环境的结果误显示为生产环境结果。历史的 `ResponseSummary`、磁盘 body 副本、保留策略和清理语义保持统一；响应体被清理后，运行摘要仍可显示，但查看正文应提示用户重新运行。

首版 IPC 在既有 workspace session 契约下扩展为：

```rust
list_debug_cases(request_id) -> Vec<DebugCase>
create_debug_case(request_id, name, case_type, spec) -> DebugCase
delete_debug_case(request_id, case_id) -> ()
history_record(..., debug_case_id: Option<Uuid>, environment_id: Option<Uuid>) -> ()
```

前端把用例加载为 `nodeId` 为空、但携带 `sourceRequestId` 与 `debugCaseId` 的独立调试标签：只有 `nodeId` 是基础 Request 的自动保存目标；`sourceRequestId` 仅供执行时解析集合/文件夹继承。这样编辑加载后的参数不会误写回基础接口，也能让运行记录保持可追溯。用例快照保存变量占位符而不保存 `ActualRequest`；密钥、Cookie、解析后的鉴权信息和完整响应始终遵守现有环境/运行态安全边界。

字段级 patch、断言、提取、批量运行、固定响应基线和独立 case 文件目录属于后续演进；在它们落地前不得以“调试用例”之名绕过历史保留、工作区 session 或大响应体约束。

### 6.3 为什么选 YAML（决策 D4，已确认）

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **YAML** | 人类可读、多行字符串（脚本/JSON body）友好、Git diff 清晰、生态成熟、有 JSON Schema 支持 | 缩进敏感、锚点等特性需限制使用 | ✅ **采用** |
| JSON | 无歧义、解析快 | 多行脚本要转义成 `\n`，diff 完全不可读 | ❌ |
| TOML | 配置友好 | 嵌套数组表达差，多行字符串一般 | ❌ |
| 自定义 DSL（如 `.bru`） | 可以做到最简洁 | 生态零、工具链要自建、用户学习成本 | ❌ |

配套措施：**公开发布 JSON Schema**（`apogee.schema.json`），用户在 VS Code 里编辑集合文件也能获得补全与校验。

**MIT 开源不会降低这条要求的重要性。** 公开 Schema 让用户、外部工具和贡献者能在不依赖应用实现细节的情况下读写、校验和生成集合文件；源码审阅、稳定数据格式和可复现 Release 共同证明「数据不在我们手里」。对应 [PRD §9.3](./01-产品设计文档.md) 的可验证本地优先策略。

同理，格式稳定性承诺（v1.0 起 Format v1 只增字段不改语义）是公开生态的兼容性契约：即使应用停止维护，用户的集合文件仍应可读、可用、可由其他工具迁移。

### 6.4 Git 友好性设计

| 设计 | 目的 |
| --- | --- |
| 一个请求 = 一个文件 | 冲突范围最小化，两人改不同接口不冲突 |
| 字段顺序固定（序列化时排序稳定） | 避免无意义 diff |
| 稳定 UUID + 独立 `name` 字段 | 重命名只改一行，不是删一个建一个 |
| 排序用 `sort_order` 整数，间隔 1000 | 插入不需要重排全部文件 |
| 不写入时间戳、不写入「最后运行结果」 | 避免每次运行都产生 diff |
| 运行态数据（历史/缓存/索引）全在 `.apogee/` 或应用数据目录 | 不污染仓库 |
| 原子写入（temp file + rename） | 崩溃不产生半截文件 |
| 文件监听（notify crate）+ 外部变更热重载 | 用户 `git pull` 后 UI 自动刷新；有本地未保存改动时提示合并 |

### 6.5 SQLite 的职责边界

SQLite **只存可重建的派生数据**，不作为集合的真相来源。这样即使数据库损坏，删掉重建即可，用户数据不丢。

```sql
-- 索引：加速树加载与搜索
node_index(id, workspace, path, parent_id, kind, name, method, url, sort_order, mtime)
-- 全文搜索
node_fts USING fts5(name, url, docs, content=node_index)
-- 历史
history(id, request_snapshot BLOB, response_meta BLOB, body_path, status, duration_ms, created_at)
history_fts USING fts5(url, body_text)  -- 可选，按设置开启
-- 运行记录
run(id, collection, started_at, finished_at, passed, failed)
run_item(run_id, request_id, status, duration_ms, asserts BLOB)
-- 响应体缓存台账（LRU 淘汰用）
response_cache(id, body_path, size_bytes, last_access_at)
```

配置：`journal_mode=WAL`、`synchronous=NORMAL`、`mmap_size` 适度、写操作批量事务。

## 7. 脚本运行时设计

### 7.1 沙箱与 API

QuickJS 上下文预热复用，每次请求创建轻量 context。暴露的 API 刻意简洁，同时提供 Postman 兼容层：

```js
// 原生 API（推荐）
apogee.req.headers.set("X-Trace", apogee.uuid());
apogee.vars.set("token", res.json().data.token);        // 默认写 runtime 作用域
apogee.vars.set("token", "...", { scope: "environment" });
apogee.expect(res.status).toBe(200);
apogee.expect(res.json().data.list).toHaveLength(10);
await apogee.sleep(100);
apogee.console.log("debug info");                        // 输出到响应区 Console Tab

// Postman 兼容层（导入的脚本无需改写即可跑）
pm.environment.set("token", pm.response.json().token);
pm.test("状态码 200", () => pm.expect(pm.response.code).to.eql(200));
pm.request.headers.add({ key: "X-A", value: "1" });
```

### 7.2 沙箱限制

| 限制 | 值 | 理由 |
| --- | --- | --- |
| 执行超时 | 默认 5s，可配置 | 防死循环 |
| 内存上限 | 32MB / context | QuickJS 原生支持内存限额 |
| 文件系统 | 无访问 | 安全 |
| 进程 / shell | 无访问 | 安全 |
| 网络 | 默认禁止；`apogee.fetch` 需在集合设置里显式开启 | 防止脚本外发数据 |
| 全局对象 | 白名单（无 `require`、无 `process`、无 `eval` 动态加载模块） | 安全 |

**兼容性坦诚说明**：`pm.*` 兼容层对齐最新版 Postman SDK 的高频子集（约 Top 30，清单见下），不可能 100% 兼容完整 SDK（含 `pm.sendRequest` 的全部行为、内置 lodash/cheerio/crypto-js 等库）。导入时对不支持的调用生成 `// TODO: apogee 暂不支持 pm.xxx` 注释并写入迁移报告，这对应 PRD §13 的 R4 风险。内置库只提供 `crypto`（hash/hmac/base64）与 `uuid` 两个最必要的。

### 7.3 `pm.*` 兼容层覆盖清单（Top 30，v0.3 交付）

| 分类 | 覆盖的 API |
| --- | --- |
| 变量 | `pm.environment.get/set/unset/has`、`pm.globals.get/set/unset`、`pm.collectionVariables.get/set/unset`、`pm.variables.get/set/replaceIn` |
| 请求 | `pm.request.url`、`pm.request.method`、`pm.request.headers.add/upsert/remove/get`、`pm.request.body` |
| 响应 | `pm.response.code`、`.status`、`.json()`、`.text()`、`.headers.get()`、`.responseTime`、`.responseSize` |
| 测试 | `pm.test(name, fn)`、`pm.expect(...)`（对齐 chai 的 `to.eql / to.equal / to.be.* / to.have.* / to.include`） |
| 信息 | `pm.info.requestName`、`pm.info.iteration`、`pm.info.eventName` |
| 控制 | `pm.execution.setNextRequest()`（Runner 内有效）、`pm.sendRequest()`（需集合级显式授权网络） |
| 兼容别名 | 旧版 `postman.setEnvironmentVariable` / `getEnvironmentVariable` / `setNextRequest` |

清单外的调用一律标注 TODO，不静默降级。清单本身随语料库回归结果调整：如果回归集里出现高频但未覆盖的 API，优先补齐。

### 8.3 Postman 导入器实现要点（对应决策 D3）

```
src-tauri/src/domain/importer/postman/
├── detect.rs          ← 从 info._postman_id / schema URL 判定版本
├── schema/            ← 官方 JSON Schema 本地副本（v2.1.0 draft-07 / v2.0.0）
├── upgrade_v1.rs      ← v1 → v2.1 升级
├── upgrade_v20.rs     ← v2.0 → v2.1 升级
├── collection.rs      ← 主转换器（v2.1 → Apogee IR）
├── environment.rs
├── globals.rs
├── vault.rs           ← Vault 密钥 → 系统钥匙串
├── dump.rs            ← Data Dump 目录批量识别
├── script.rs          ← pm.* → apogee.* 转译 + 不支持项标注
└── report.rs          ← 迁移报告生成
```

关键实现约束（**已按 Spike S6 实测结果修订**）：

1. **版本探测靠内容，不靠文件名**：读 `info.schema` 字段的 schema URL 判定版本；缺失时按结构特征回退推断。
   S6 验证：23/23 个真实文件都能从 `info.schema` 读到版本，这条成立。
   ⚠️ 但 v1 格式没有 `info` 字段，必须走结构推断（`order` / `requests` 特征），**该分支目前没有测试覆盖**，需单独补。

2. **schema 校验必须在版本升级之后执行** —— 这条是 S6 改的。
   原文写的是「schema 校验先行」，实测证明顺序反了：一律用 v2.1.0 schema 校验时通过率只有 20/23（87%），失败的 3 个**全是 v2.0.0 格式的文件**；先按探测版本匹配对应 schema，通过率 23/23（100%）。
   典型差异是 auth 表示法：v2.0 用对象 `{"oauth2": {...}}`，v2.1 改成了 `{key, value, type}` 数组。
   所以 `upgrade_v20.rs` / `upgrade_v1.rs` **不是可选优化，是必需的前置步骤**。正确流水线是：
   `探测版本 → 升级到 v2.1 → 严格校验`。

3. **oneOf/anyOf 失败时不能直接用校验器的错误** —— 这条是 S6 新增的。
   原文承诺「报错精确到 JSON Pointer 级字段路径」。实测做不到：**100% 的校验错误都来自 `oneOf`/`anyOf` 关键字**，这类错误只报「不匹配任何分支」，路径停在容器层（如 `/item/0`），并把整棵子树 dump 进错误消息 —— 既定位不到具体字段，也无法展示给用户。
   落地做法：拿到 `oneOf` 失败后，自己按判别字段（`item` 看有无 `request`、`auth` 看 `type`）选定**预期分支**，再对该分支单独校验，才能得到可用的字段级报错。

4. **官方 schema 与真实文件可能不一致时降级为警告**：策略是「校验失败降级为警告 + 记录到迁移报告」，绝不因为校验不通过就拒绝导入。
   S6 后这条的定位从「默认策略」调整为「**兜底策略**」：按第 2 条升级之后，真实文件是 100% 通过的，所以校验可以作为硬门槛（能挡住真正损坏的文件）；只有升级后仍失败的才降级为警告继续解析。

5. **保留原始片段**：所有无法转换的内容以注释形式保留在生成的 YAML 里，用户可自行修补

6. **只维护 draft-07 一份本地 schema 副本**。官方同时提供 v2.1.0 的 draft-04（55081 字节）与 draft-07（52960 字节）两个变体，文件内容不同，但 S6 实测对 23 个真实文件的判定结果**完全一致**（0 处分歧）—— 差异只在 schema 写法层面。维护两份没有收益。

7. **`jsonschema` crate 必须 `default-features = false`**。默认 feature 带远程 `$ref` 解析，会把 `reqwest` + `hyper` + `rustls` 整条 HTTP 栈拖进依赖树。我们用的是本地 schema 副本，不需要联网解析 —— 这对「安装包 < 15MB」是实打实的差别。

**性能**：不是瓶颈。S6 实测 2.76 MB 的真实集合（981 个请求）校验耗时 1.37 ms，23 个文件合计 7.0 ms。schema 校验完全可以放在导入预览的同步路径上，不需要异步化。

**原则**：导入器的质量直接决定 PRD §11 的激活率指标。为此建立**语料库回归**：收集 100+ 真实导出文件放进 CI（其中 Postman 系不少于 40 个，覆盖各版本与各类导出物），每次改动都跑，保证「导入成功率 > 90%」可度量。

### 10.3 过程中的工程教训

这些不是关于 Apogee 的，是关于「怎么做量测」的，值得写进工程规范：

1. **配置项不能有两个来源。** S2 首轮四个用例全部失败于 `TypeError: Failed to fetch`，根因是 CSP 写了两份：`index.html` 的 meta 里只放了 `apogee:`，漏了 Windows 上实际使用的 `http://apogee.localhost`（Tauri 在 Windows/Android 把自定义协议映射成 `http://<scheme>.localhost`），协议请求被静默拦掉。已改为 CSP 只由 `tauri.conf.json` 提供。

2. **量测台必须能报告失败，不能只靠超时。** 同一轮里 `CodeMirrorView` 加载失败时只在界面上显示错误、没有把失败传回量测台，导致四个用例各等 30 秒超时且拿不到根因。修法有两条：给组件加 `failed` 事件，以及在正式量测前加一个**协议自检**步骤，把诊断信息在最靠近失败点的地方取出来。

3. **指标必须钉死口径，否则等于没定指标。** S1 第一版按「各进程 `WorkingSet` 求和」报出 449MB 空闲内存，差点得出「架构不可行」的错误结论 —— WebView2 子进程映射同一批 msedge DLL，共享页被重复计数，放大 2.88×。同一组数据换三种口径分别是 155.7 / 449.0 / 224.2MB，**其中两种能让 dbx 与 Apogee 的排序完全反过来**。正确口径是私有工作集（`Working Set - Private`）。已在 PRD §5.1 补「量测口径」小节。

4. **进程树是需要校验的推断，不是可以直接读取的事实。** Windows 复用 PID，而 `Win32_Process.ParentProcessId` 只是一个数字不带世代信息：真正的父进程退出后，它的 PID 可能被我们的进程占用，于是无关进程看起来就成了后代。S1 中过一次 —— 某轮把另一个应用的 13 个进程算进内存（147MB → 430MB），**而且 `Stop-ProcessTree` 按同一份名单把它们杀掉了**。量测台测错可以重跑，动了被测对象之外的东西不行。两道防线：父子边逐条校验创建时间（子不早于父），以及树内映像名白名单，越界时统计报错、杀进程跳过。

5. **量测台自己要报告环境噪声。** 同一份二进制在有/无背景负载下启动耗时差近 2 倍（545ms vs 1500ms）。不记录量测期间的 CPU 负载，报出来的数字就无法判断能不能引用。S1 的做法：每轮启动前等 CPU 降到 20% 以下再拉起进程，记录实际起跑负载与「没等到就开跑」的轮次，并在报告顶部显式声明启动值是上限还是基准。

6. **跨进程计时的起点和终点都不能靠推断。** 终点必须由被测进程自己上报（S1 用应用在首帧后写环境变量指定的标记文件，原子 `tmp` + `rename` 并校验 PID）——用「窗口出现」会被兜底 `show()` 污染，用「进程存在」在 WebView2 还在加载时就已成立。起点要用内核的 `Process.StartTime`，不是 `Start-Process` 返回后启动的秒表（后者含 cmdlet 开销与轮询粒度，实测高估中位 17ms）。

7. **跨进程传时刻要传数字，不要传格式化后的时间字符串。** S3 让应用把驻留窗口的截止时刻写进阶段文件，第一版写的是 ISO 8601 字符串，量测台读出来一律「窗口内只采到 0 个样本」。根因是 PowerShell 的 `ConvertFrom-Json` 会把 ISO 串自动转成 `DateTime`，再 `[string]` 一次就把时区丢了，UTC 值被当本地时间重新解析 —— 截止时刻整整偏掉一个时区偏移量。改成 epoch 毫秒数后即正常。S1 的就绪标记用 `readyEpochMs` 而不是时间串，是同一个理由；这条应当作为规范：**跨进程/跨语言边界只传纪元数字**。

8. **贴着 vsync 的性能指标是饱和读数，只能证伪不能定量。** S3 第一版报出「1000 / 5000 / 20000 节点首渲都是 26.7ms、三档 fps 都是 75.0、掉帧都是 0%、展开折叠都是 26.7ms」，看着像「性能与规模完全无关」的漂亮结论 —— 实际那些数字全是**显示器节奏**：26.7ms 就是 2 个 vsync（75Hz 下 2×13.3ms），只要单帧工作量低于一帧预算，任何实现都会报出同一组数。修法是并行报两套口径：不含 vsync 等待的 `patch`（Vue 打完 DOM）+ `layout`（读 `offsetHeight` 强制同步排版）+ 单步滚动成本，以及含 vsync 的「首帧 / 到像素上屏」。前者回答「我们的代码有多快、还剩多少余量」（实测单步 0.9ms / 一帧预算 7%，余量约 14 倍），后者回答「用户等了多久」。**只报后者会让一个只有 5% 余量的实现和一个有 14 倍余量的实现看起来一模一样。**

9. **`performance.now()` 被钳到 0.1ms，微量测必须重复取平均。** S3 第一版单次测那趟 O(N) 可见性过滤，1040 / 5000 / 20000 节点读出 0.00 / 0.30 / 0.10ms，于是差点写出「20 倍节点数只慢 1 倍」。那不是数据，是量化噪声。重复 200 次取平均后是 0.015 / 0.040 / 0.097ms，随规模增长的趋势才显出来。

10. **量测台不能一边施压一边采样。** 采一次进程树内存要跑两条 CIM 查询（`Win32_Process` + `Win32_PerfRawData_PerfProc_Process`），几百毫秒的 CPU —— 在帧率量测期间做这件事，测出来的掉帧有一部分是量测台自己造的。S3 的做法是两阶段协议：被测应用把进度写进阶段文件，帧率阶段量测台绝不碰进程树，应用跑完后进入一个「驻留窗口」并申报截止时刻，量测台只在窗口内采样，采完校验阶段没变过。顺带发现原来的采样实现是 O(树大小 × 进程总数)（每个进程都 `Where-Object` 扫一遍全表），机器上 500+ 进程时单次采样要一两秒 —— **量测台自己的开销也是噪声源**。

11. **同一个指标在不同状态下量出来不是同一个数，状态必须写进指标定义。** S3 跑完帧率矩阵（5 次组件创建/销毁，其中两次铺过 1040 和 5000 行真实 DOM）之后立刻量内存，得到 208.0MB 中位 / 246.2MB 最差；干净启动直接进同一个驻留状态，是 158.8MB / 168.6MB。差的约 50MB 几乎全在 `renderer`，十几秒内不回落。两个数都对，但只有后者能用来定预算 —— 用前者等于把量测台自己的开销算进产品预算。所以 S3 为每种配置起两组进程，两个数都报。**差值本身也是结论**：反复创建销毁大列表的内存不会立刻还回来，标签虚拟化要按这个前提设计。

13. **内存要跨多次启动取值，一次不算。** 同一份二进制、同一个驻留状态，5 次启动的私有常驻峰值实测跨度 **9.1%**（154.6 / 160.9 / 160.3 / 160.4 / 168.6 MB）——WebView2 的 GPU/着色器缓存状态不同就能造出这个差。拿单次数字去定预算，等于把预算建在一次抽样上。

14. **起跑 CPU 门禁挡不住「整段偏移」型污染。** 重跑 S1 时遇到一次干净的双峰：前 11 轮启动 788～1234ms / 前端 mount 145～219ms，第 12 轮起 553～638ms / 61～74ms，而**每一轮的起跑 CPU 都通过了 20% 门禁**。最可能的原因是刚构建完的二进制被 Defender 首扫。这种污染既躲过了 CPU 门禁（它只看瞬时负载），也躲过了「超过中位 2 倍」的离群判定（它不是个别离群，是整段偏移），混进一个中位数会同时污染冷启动和热启动两个结论。已给 S1 量测台加上**预热漂移检测**：比较前后两半轮次的中位，差值超过 30% 就在报告顶部标红并指出「要引用请用后半段中位或 `-SkipBuild` 重跑」。复跑后漂移 -0.9%，数字与改动前的基线完全一致（mount 66.4ms vs 66.7ms），从而也确认了 S3 的那些前端改动没有影响启动。

12. **配置开关生效与否必须验证，不能相信自己设过。** S3 用 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 关硬件加速，量测台会断言那些 flag **确实出现在 WebView2 浏览器进程的命令行上**，不然就报错退出。理由很实际：如果开关静默失效，测出来的是「关 GPU 也不省内存」，而这个错误结论会直接导致一个正确的优化方向被否掉。同一次量测还纠正了一个想当然：**`--disable-gpu` 不会让 `gpu-process` 消失** —— 现代 Chromium 退到 SwiftShader 软件光栅化，进程照旧存在（77.2MB → 10.7MB），进程数不变。

### 10.4 内存门槛定稿（S1 提出，S3 定案）

S1 是唯一判定 FAIL 的 Spike，但失败位置不在实现里，而在**指标本身定得没有实测依据**。它留下三项待决，其中两项依赖 S3 的数据。S3 跑完，结论如下。

#### 已决

| 原门槛 | 决定 | 依据 |
| --- | --- | --- |
| §10.1「空闲 < 80MB」 | **废弃。** 这是纸面估算，Windows + WebView2 上空壳地板就是 155.7MB，其中可控的 Rust 侧只有 3.71MB | S1 |
| §10.1「启动 < 400ms」 | **废弃。** 同上，启动的 86% 花在第一行 JS 之前。对外承诺沿用 PRD §5.1 的 800ms 冷启动（实测 608.5ms，达标） | S1 |
| PRD §5.1「空闲常驻内存 < 150MB」 | **选 (a)：按平台分别定预算。Windows 改为 < 220MB**，macOS 待量测后单独设定。推导过程写进 [PRD §5.1「内存预算怎么来的」](./01-产品设计文档.md) | S1 + S3 |
| 缺一条可控门禁 | **新增「Rust 主进程私有常驻 < 20MB」。** 这是整个内存预算里唯一由我们的代码决定的部分（中位 3.7～3.8MB、峰值 9.3MB），回归门禁盯它才有意义 | S1 + S3 |
| PRD §5.1「50 标签 < 400MB」 | 随基线上调为 **< 450MB**（= 220 基线 + 230 增量预算），仍标注未量测，需标签虚拟化落地后补 | 推导 |

**220MB 的依据**：最差观测 **171.5MB**（S1 空壳峰值；S3 负载条件下的最差是 168.6MB，两者基本重合），加约 28% 余量。跨启动波动实测最高 **9.1%**（约 14MB），预算得先容纳这一项。余下的余量留给尚未落地的 SQLite、Cookie Jar、脚本引擎，它们都在 Rust 侧，而 Rust 侧中位只占 3.8MB。同栈成熟产品 [dbx](https://github.com/t8y2/dbx) 在同一台机器上是 188～194MB，可作旁证：~155MB 以上是 WebView2 在 Windows 上的起步成本，不是实现质量问题。

**一个值得记住的观测**：从空壳到「1 工作区 + 3 标签 + 5000 节点集合树」，进程树中位只涨了 **3.1MB**（155.7 → 158.8），比跨启动波动还小。所以内存预算的风险不在集合规模，而在两处：一是 Rust 侧新增常驻结构（S2 那个 91MB 的索引就是例子），二是反复创建销毁大列表后的残留（见「仍待做」）。

#### 选项 (b) 的处置：关硬件加速，可行但不采用

S1 发现 `gpu-process` 单独占 67MB（空闲内存的 46%），所以 §10.4 原来留了「从 WebView2 侧找真实节省」这条路，并注明**须先做 S3**（因为要拿滚动帧率去换）。S3 的答案：

| | GPU 开（默认） | GPU 关（`--disable-gpu --disable-gpu-compositing`） |
| --- | --- | --- |
| 进程树私有常驻（干净驻留，5 轮中位 / 最差） | 158.8 / 168.6MB | **94.0 / 98.0MB**（省 70.6MB / 41.9%） |
| 跨启动波动 | 9.1% | 3.1% |
| `gpu-process` 私有常驻 | 71.3MB | 10.7MB（**进程仍在**，退到 SwiftShader） |
| 进程数 | 7 | 7 |
| 5000 节点滚动掉帧率 | 0.00% | **0.00%** |
| 单步滚动主线程成本 | 0.9ms | 0.8ms |

**技术上可行 —— 关掉就能压到 98MB，连原来的 150MB 都够 —— 但决定不采用它作为达标手段。** 理由不是数字不好，而是**证据覆盖面不够**：「没有代价」只在一种负载下验证过，即文本行列表滚动，而那种负载对合成器极轻（滚动时只更新 35 行纯文本，单步成本占一帧 7%）。`--disable-gpu` 是全局开关，CodeMirror 滚动大文档、响应体树大面积重绘、全屏 4K 下的软件合成全都会被牵连，这些一个都没测。**用一个测过的指标去换几个没测过的指标不叫优化。**

处置：记为一项**已量化的可选优化**（价值 70.6MB）。后续若要启用，前置条件是先量 CodeMirror 与响应体树在软件合成下的帧率；即便通过，也应作为用户可选的「低内存模式」，不进默认配置、不作为达标依据。
