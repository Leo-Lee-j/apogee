## 1. 一句话定位

**Apogee 是一个本地优先、启动即用的桌面 API 客户端：Postman 的核心能力，1/10 的资源占用。**

Slogan 候选：
- 「快，是唯一的功能。」
- 「打开就能发请求。」

1. **自定义协议 scheme 变更。** Rust 注册处（`src-tauri/src/lib.rs`）、CSP（`tauri.conf.json`，含 Windows 的 `http://<scheme>.localhost` 形态）、前端 URL 构造（`src/ipc/index.ts` 的 `PROTOCOL_SCHEME`）三处必须同时改。漏一处的表现是 `TypeError: Failed to fetch` —— 被 CSP 静默拦掉且不报 CSP 违规，很难定位（这个坑 S2 已经踩过一次，见 [03 文档 §10](./03-技术架构与数据模型.md)）。
2. **S1 就绪标记环境变量变更**（`APOGEE_S1_READY_FILE`）。Rust 侧与 `scripts/measure-s1-windows.ps1` 两处必须一致，否则 S1 量测会一直等到超时。
3. **bundle identifier 变更为 `app.apogee.desktop`。** 这会改变应用数据的落盘位置。项目处于 v0.1 骨架期、尚无真实用户数据，所以不需要迁移逻辑；**若在正式发布后再改名，则必须提供数据目录迁移**。

`spikes/results/*.json` 与 `*-report.md` 是历史实测产物，保留当时的名字不改 —— 改了就不再是「当时实测到的东西」。

## 2. 产品愿景与问题定义

### 2.1 用户真实痛点

你提出的出发点是「Postman / Apifox 太卡、占用高」。把这句话拆成可验证的问题，才能变成可设计的产品：

| 痛点 | 具体表现 | 根因 |
| --- | --- | --- |
| 启动慢 | 双击到能发第一个请求要 5～15 秒 | Electron 全量 Chromium 启动 + 启动时同步云端工作区 |
| 常驻内存高 | 空闲 600MB～1.5GB | 多进程 Chromium + 全量加载集合/历史到内存 |
| 大响应体卡死 | 返回 5MB JSON 后界面掉帧甚至无响应 | 主线程解析 + Monaco/DOM 全量渲染整棵 JSON 树 |
| 多标签劣化 | 开到 20+ 标签明显变慢 | 每个标签保留完整编辑器实例，不做卸载 |
| 强制登录 / 云绑定 | 不登录无法用核心功能，离线场景受限 | 商业模式驱动的账号体系 |
| 界面重 | 功能入口过多，日常只用 20% | 从「API 客户端」演化成「API 全生命周期平台」 |

### 2.2 我们的判断

市面上已经形成了一波「轻量、本地优先、Git 友好」的替代品浪潮（Bruno、Hoppscotch、Insomnia、Yaak 等），其中 Yaak 已经在用 Tauri + Rust + React 的组合，验证了这条技术路线可行（[Yaak 项目说明](https://github.com/mountain-loop/yaak)、[Postman 替代品盘点](https://qodex.ai/blog/postman-alternatives)）。

这波替代品大多已经开源；Apogee 现在也以 MIT 许可证公开源码（见根目录 `LICENSE`）。开放、可审计与社区协作成为基本门槛，而不是可以替代产品能力的标签；我们的机会仍必须建立在竞品尚未做好的地方。

所以 **Apogee 的机会不在「又一个轻量客户端」，而在三个具体缺口**：

1. **中文用户体验缺口**：Bruno / Yaak 的中文本地化、中文文档、国内网络环境（代理、证书、企业内网）适配都很弱；Apifox 补上了这块但又变重了。
2. **性能承诺缺口**：所有竞品都说自己「轻量」，没有一个把性能当作**可验证的产品规格**写进文档并在 CI 里守住。
3. **迁移成本缺口**：从 Postman/Apifox 搬家往往丢脚本、丢环境、丢鉴权配置。谁能做到「导入即可用」，谁就拿到用户。

### 2.3 反目标（明确不做）

写清楚不做什么，比写做什么更重要。以下内容在 v1.0 之前**不做**：

- ❌ 不做 API 文档管理平台、不做接口设计协作、不做数据字典
- ❌ 不做强制账号体系；不做「不登录就残废」
- ❌ 不做云端集合托管（协作交给 Git）
- ❌ 不做 Mock Server（v1.5 再评估）
- ❌ 不做 CI 报告平台 / 监控大盘
- ❌ 不做浏览器版、不做移动端
- ❌ 不做遥测上报（默认零采集，见 §10.2）

每加一个功能，先回答：**它会不会让冷启动变慢 10ms？** 会，就要重新论证。

## 3. 目标用户

### 3.1 用户画像

**P0 — 后端 / 全栈工程师（主要用户，占比预估 65%）**
> 「我一天要发几百个请求，我只要地址栏、Body、响应体，和一个能记住我上次改了什么的东西。」

- 场景：本地联调、查线上问题、写完接口自测
- 关键需求：极速启动、快捷键闭环、变量替换、请求历史可回溯
- 决策因素：够快 + 迁移不痛

**P1 — 测试工程师（占比预估 20%）**
> 「我要把 30 个接口串成一条链路跑一遍，看断言过没过。」

- 场景：接口回归、链路测试、造数据
- 关键需求：Collection Runner、断言、变量提取链、CSV 数据驱动、CLI 可跑

**P2 — 前端工程师（占比预估 15%）**
> 「后端接口给我了，我要看清返回结构，最好直接生成 TS 类型。」

- 场景：对接接口、Mock 数据来源、排查跨域和鉴权
- 关键需求：响应体结构可视化、cURL 导入导出、代码片段生成

### 3.2 核心用户旅程（Day-1）

```
下载安装（<15MB，30 秒）
  → 打开（<1 秒，无登录墙）
  → 引导：「从 Postman 导入」/「粘贴 cURL」/「空白开始」
  → 3 秒内发出第一个请求
  → 保存到集合 → 选择本地目录（看得见的文件，不是黑盒数据库）
  → 提交到 Git → 同事 clone 即可用
```

**首次成功请求时间（Time-to-First-Request, TTFR）目标：< 20 秒**，含安装后首启动。这是本产品最重要的单一体验指标。

## 4. 产品设计原则

按优先级排序，冲突时上位原则胜出。

1. **性能是功能（Performance is a Feature）**
   每个需求评审必须附带性能影响评估。性能预算（§5）是硬约束，不是目标。

2. **本地优先（Local-First）**
   数据默认在用户磁盘上，以人类可读的文本文件存放。断网、不登录，功能 100% 可用。云是可选增强，不是前置依赖。

3. **键盘优先（Keyboard-First）**
   所有高频操作必须有快捷键，且能通过 `Ctrl/Cmd+K` 命令面板到达。鼠标是备选路径。

4. **渐进披露（Progressive Disclosure）**
   默认界面只暴露 20% 的高频功能。脚本、断言、代理、证书等能力存在但不占视觉预算。

5. **零意外（No Surprises）**
   不自动上传、不自动更新覆盖用户数据、不静默改写用户文件格式。所有写盘操作可预期、可 diff。

6. **可迁移、可退出（No Lock-in）**
   支持完整导入导出。用户想走随时能走，这反而是留下来的理由。

## 5. 性能预算（产品硬指标）

这是本产品的**规格书**，不是愿望。全部指标写进自动化基准测试，回归即阻断合并（见 §5.2）。

### 5.1 指标表

| 指标 | Apogee 目标 | Postman/Apifox 参考量级 | 测量条件 |
| --- | --- | --- | --- |
| 安装包体积 | **< 15 MB** | 150～300 MB | Windows x64 安装包 |
| 磁盘占用（安装后） | **< 50 MB** | 500 MB+ | 不含用户数据 |
| 冷启动到可交互 | **< 800 ms** | 5～15 s | 首屏可输入 URL 并发送。计时口径见下方「量测口径」 |
| 热启动 | **< 300 ms** | 2～5 s | 进程已缓存（OS 文件缓存已热） |
| 空闲常驻内存（**Windows**） | **< 220 MB** | 600 MB～1.5 GB | 打开 1 个工作区、3 个标签。**口径：进程树私有工作集峰值**。数值依据见下方「内存预算怎么来的」 |
| 空闲常驻内存（macOS） | **待量测后设定** | 同上 | WKWebView 进程模型与内存口径都不同，不能套用 Windows 的数字 |
| **Rust 主进程私有常驻** | **< 20 MB** | — | 同上条件。**这是整个内存预算里唯一由我们的代码决定的部分**，回归门禁盯它 |
| 50 标签内存 | **< 450 MB**（未量测） | 明显劣化 | 50 个标签，其中 1 个活跃。= 220 MB 基线 + 230 MB 增量预算，需标签虚拟化落地后量测 |
| 集合树渲染 | **< 100 ms** | — | 1000 个请求的集合首次展开 |
| 请求发送开销 | **< 5 ms** | 30～100 ms | UI 触发到 socket 写出（排除网络 RTT） |
| 10 MB JSON 响应首屏 | **< 300 ms** | 数秒或卡死 | 状态行 + 首屏内容可见可滚动（按 [02 §4.4](./02-交互与界面设计.md) 分级降级高亮） |
| 100 MB 响应体 | **不崩溃、可预览** | 通常崩溃 | 降级为摘要 + 流式预览模式 |
| 输入延迟 | **< 16 ms** | 偶发掉帧 | 编辑器连续输入 P99 |
| Collection Runner | **1000 请求 / < 60 s** | — | 并发 10，本地 mock 服务 |

#### 量测口径（Spike S1 补充）

指标不写清口径就等于没写。同一个 Apogee 空壳按三种常见内存口径分别是 **155.7 MB / 449.0 MB / 224.2 MB** —— 相差近 3 倍。所以以下两条必须钉死：

- **内存 = 进程树私有工作集（`Working Set - Private`）峰值。** 「进程树」指 `apogee.exe` 及其全部 WebView2 子进程（Windows 上共 7 个进程）；「私有工作集」是常驻且不与其它进程共享的物理内存，等于任务管理器「内存」列。
  - **不用** 各进程 `WorkingSet` 求和：WebView2 子进程映射同一批 msedge DLL，共享页被重复计数，实测放大 **2.88×**。
  - **不用** `PrivateMemorySize64` / 提交量：那是申请的地址空间，不是占用的物理内存，实测高估约 **44%**。
- **启动 = 内核记录的进程创建时刻 → 应用首帧就绪时刻。** 用 `Process.StartTime` 作起点、应用自己写的就绪标记作终点，跨进程量测。**不能只看前端 `performance.now()`** —— 实测启动耗时的 **85%** 花在第一行 JS 之前，前端自计时会系统性低估。

#### 内存预算怎么来的（Spike S1 + S3 定稿）

原来这里写的是「< 150 MB」，没有实测依据。S1、S3 把它量出来了，结论是**这个数在 Windows 上不可达**，因此按平台重定为 **220 MB**。推导过程如下，任何人都应该能据此复核或推翻：

| 观测 | 配置 | 进程树私有工作集 | 来源 |
| --- | --- | --- | --- |
| 空壳（1 个空标签、无集合、无 SQLite） | 默认 | 中位 155.7 MB / 峰值 **171.5 MB** | S1（20 轮启动） |
| **1 工作区 + 3 标签 + 5000 节点集合树** | 默认 | 中位 158.8 MB / 最差 168.6 MB | S3（5 轮干净启动） |
| 同上 | 关硬件加速 | 中位 94.0 MB / 最差 98.0 MB | S3（5 轮） |
| 同上，且刚跑完一轮重渲染会话 | 默认 | 中位 208.0 MB / 最差 246.2 MB | S3 |
| dbx 0.5.70（同栈成熟产品，实际使用中） | 默认 | 188.4 ～ 194.3 MB | S1 手工量测 |

**220 MB 的构成**：最差观测 **171.5 MB** + 约 28% 余量。跨启动波动实测最高 **9.1%**（WebView2 的 GPU/着色器缓存状态不同），预算必须先容纳这一项。余下的余量留给尚未落地的 SQLite、Cookie Jar、脚本引擎 —— 这些都在 Rust 侧，而 Rust 侧当前中位只占 3.8 MB，所以 48 MB 的余量是宽松的。

**为什么不是「优化到 150 MB」**：158.8 MB 里 `gpu-process` 一个进程就占 71.3 MB（45%），`browser` 37.6 MB，`renderer` 28.1 MB，**Rust 侧只有 3.8 MB**。分母由 WebView2 定死，我们能动的是那 3.8 MB。把预算定在做不到的地方，只会让门禁长期挂红然后被忽略。

**一个反直觉的观测：我们自己的负载几乎量不出来。** 空壳中位 155.7 MB，加上 1 个工作区 + 3 个标签 + 一棵 5000 节点集合树之后是 158.8 MB —— **只涨了 3.1 MB，比跨启动波动（9.1%，约 14 MB）还小**，峰值甚至互有高低（171.5 vs 168.6）。原因看 §5.1.1 的第 3 条：虚拟滚动让 DOM 量与集合规模无关（实渲染恒为 35 行），标签只是轻量状态对象。含义有两面：好的一面是集合规模不会吃掉内存预算；需要警惕的一面是**这个预算里 90%+ 的变动与我们的代码无关，所以「总量没涨」不能当作「我们没有引入内存问题」的证据** —— 那要看 Rust 主进程那一条门禁。

**关掉硬件加速能压到 98.0 MB，但不采用它作为达标手段。** S3 实测 `--disable-gpu --disable-gpu-compositing` 能省 70.6 MB（41.9%），且在集合树滚动场景下掉帧率仍是 0%、单步主线程成本没变差。不采用的理由：这个开关是全局的，而「没有代价」只在一种负载（文本行列表滚动）下验证过 —— CodeMirror 滚动大文档、响应体树大面积重绘、全屏 4K 下的软件合成都没测。用一个测过的指标去换几个没测过的指标不是优化。它记为**一项已量化的可选优化**（见 [03 §10.4](./03-技术架构与数据模型.md)），将来可能作为用户可选的「低内存模式」提供，但不进默认配置、不作为达标依据。

> 顺带一条口径补充：**「关掉硬件加速就少一个进程」是错的。** 传 `--disable-gpu` 之后 Chromium 退到 SwiftShader 软件光栅化，`gpu-process` 照旧存在，只是从 71.3 MB 缩到 10.7 MB，进程数不变（仍是 7 个）。

### 5.1.1 已验证的基线（Spike 实测）

指标不能只写在文档里。以下是已经在真机上测出来的数字，其余项仍是待验证目标：

| 指标 | 目标 | 实测 | 预算占用 | 来源 |
| --- | --- | --- | --- | --- |
| 安装包体积 | < 15 MB | **1.29 MB**（NSIS） | 9% | Spike S1 |
| 冷启动到可交互 | < 800 ms | **608 ms** | 76% | Spike S1 |
| 空闲常驻内存（Windows，1 工作区 + 3 标签 + 5000 节点树） | < 220 MB | **158.8 MB** 中位 / 168.6 MB 最差 | 72% / 77% | Spike S3 |
| Rust 主进程私有常驻 | < 20 MB | **3.8 MB** 中位 / 9.3 MB 峰值 | 19% / 47% | Spike S1 + S3 |
| 集合树渲染（1000 请求首次展开） | < 100 ms | **26.6 ms** | 27% | Spike S3 |
| 10 MB JSON 响应首屏 | < 300 ms | **25.3 ms** | 8% | Spike S2 |
| 100 MB 响应体 | 不崩溃、可预览 | 首屏 21.2 ms，进程存活 | — | Spike S2 |
| 首屏 JS+CSS 体积 | < 150 KB gzip | **101.9 KB** | 68% | Spike S5 |
| Postman 集合导入成功率 | > 90% | **100%**（23/23，需版本升级前置） | — | Spike S6 |

参考基线（不是指标）：空壳（1 个空标签、无集合）在 Windows 上是 155.7 MB 中位 / 171.5 MB 峰值（S1，20 轮）。它是**地板**，用来判断新增功能的内存增量是否合理，不用来判定达标。

三个额外验证到的架构论点：

1. **按 Range 取响应体首屏分片的耗时与响应体总大小无关** —— 1 MB / 10 MB / 50 MB / 100 MB 四档实测都落在 2.9～4.4 ms。作为对照，把 10 MB 全量拉进 JS 并拼成字符串要 128.9 ms，慢 31 倍。这是「大响应体不卡」能成立的根本原因，不是调参调出来的。（S2）
2. **启动与内存的地板都由 WebView2 决定，不由我们的代码决定。** 启动耗时中位 590 ms 里有 506 ms（**86%**）花在第一行 JS 之前；空闲内存 155.7 MB 里 Rust 主进程只占 **3.71 MB**（2.4%），其余在 6 个 WebView2 子进程中（单个 `gpu-process` 就 75 MB）。含义：继续压前端首屏体积的边际收益很小，而 Rust 侧每省 1 MB 都直接变成余量。（S1）
3. **集合树的渲染成本与节点数解耦，与 §5.1 的「1000 请求 < 100 ms」不是同一回事。** 实渲染行数由视口高度定死（本次 35 行），1000 / 5000 / 20000 三档都一样；随节点数增长的只有一趟 O(N) 的可见性过滤，20000 节点也只要 **0.097 ms**（占一帧预算的 0.7%）。所以「集合树渲染」这项指标真正该盯的不是「1000 请求」这个规模，而是**渲染量是否与规模无关**。同一个架构模式在 S2（Range 取首屏）和 S3（虚拟滚动）各出现一次：**把成本与规模解耦，而不是把成本优化小。**（S3）
4. **滚动帧率这类贴着 vsync 的指标是饱和读数，定量要另找口径。** 三个规模档位的帧间隔 p50 一律 13.30 ms、掉帧一律 0% —— 那是 75 Hz 显示器的节奏，不是我们的性能。真正能回答「还剩多少余量」的是不受 vsync 影响的单步主线程成本：**0.8～1.0 ms，占一帧预算的 7%，余量约 14 倍**。写性能门禁时要注意这个区别，否则一个只剩 5% 余量的实现和一个有 14 倍余量的实现看起来完全一样。（S3）

体积一项余量极大（安装包用掉 9%），前提是 release profile 保持 `opt-level="z"` + `lto="fat"` + `strip`，且 WebView2 走 `downloadBootstrapper` 不打进安装包。

未验证项：热启动（S1 实测 p95 746 ms，**未达标**，但受量测机背景负载影响，需空闲机器复测）、50 标签内存（需标签虚拟化落地）、磁盘占用（安装后）、请求发送开销、输入延迟、Collection Runner、macOS 全部指标。另有三项虽已量测但边界要记住：内存只覆盖 Windows 且驻留窗口仅十几秒（回答不了「开一天会不会涨」）、集合树帧率只覆盖主线程驱动的滚动（不含真实滚轮的输入延迟）、软件合成下 CodeMirror 与响应体树的帧率没测（这是「关硬件加速换 70.6 MB」能否采纳的前置条件）。这些要在 v0.1 期间逐项补上量测，不能靠推断。

### 5.2 性能守门机制

- `cargo bench` + 前端 Vitest bench 纳入 CI，指标回退 > 10% 直接 fail
- **首屏体积门禁已可用**：`node scripts/measure-bundle.mjs`，首屏 gzip 超 150 KB 即 fail，并额外断言 CodeMirror 不在首屏 chunk（这条比体积数字更容易被无意破坏）
- **启动与体积门禁已可用（Windows）**：`pnpm spike:s1`（复用构建产物用 `pnpm spike:s1:nobuild`），任一门槛未过即以非零码退出。三个设计要点：① 每轮启动前等 CPU 降到 20% 以下，否则测到的是「机器当时多忙」而不是「应用多快」；② 就绪信号由被测应用自己写文件上报，不用「窗口出现」或「进程存在」推断；③ 拿不到私有工作集计数器、或进程树里出现非预期映像时**直接报错而不是按 0 计入** —— 量测台必须能报告失败
- **渲染与负载内存门禁已可用（Windows）**：`pnpm spike:s3`（复用产物用 `pnpm spike:s3:nobuild`）。它是「1 工作区 + 3 标签 + 5000 节点集合树」这个条件下的帧率 + 内存门禁，也就是上表内存指标的量测台。四个设计要点：① 帧率阶段量测台**绝不采样进程内存** —— 采一次样要跑两条 CIM 查询，那点 CPU 足以自己造出掉帧，被测应用通过阶段文件告知量测台何时可以采；② 内存跨多次启动取值，单次启动波动实测 4.8%～10%；③ 内存必须在**干净启动**的进程里量，跑完帧率矩阵之后的驻留内存含约 50 MB 会话残留（在 `renderer`，十几秒内不回落）；④ 帧率不按「fps ≥ 60」判定而按掉帧率判定 —— 在 60/75 Hz 显示器上 fps 有物理上限，采样噪声就能让达标的实现「不达标」
- 两个量测台共用 `scripts/lib/ProcessTreeMemory.psm1`：进程树遍历、私有工作集口径、CPU 噪声观测只有一份实现。两个量测台各抄一份口径，就是给「改了一边忘了另一边」留后门 —— 而口径不一致会让两份报告的数字不可比，正是 §5.1「量测口径」要防的事
- 每个 Release 附带**性能报告**，公开在 Release Notes 里（这本身是营销资产）
- 内置 `帮助 → 性能自检` 面板：展示当前进程内存、各标签内存占用、最近 100 次请求耗时分解（DNS / TCP / TLS / TTFB / 下载）。
  **内存必须报整个进程树的私有工作集，不能只报 Rust 进程**（实测只占 2.5%，只报它等于骗自己）；启动耗时同理不能只报前端自计时

> 性能预算的具体实现策略见 [03-技术架构与数据模型 §4](./03-技术架构与数据模型.md)。

### 6.2 MVP 定义（v0.1，「能替代日常 80% 使用」）

一句话验收标准：**一个后端工程师能整天只用 Apogee 不打开 Postman。**

范围：
- HTTP 请求全流程（方法、URL、Params、Headers、4 类 Body、基础鉴权）
- 集合 / 文件夹 / 请求树，本地文件存储
- 单环境变量 + `{{var}}` 替换
- 响应查看（JSON 高亮 + 折叠、Headers、状态/耗时/体积）
- 请求历史
- cURL 导入导出
- 标签页、命令面板、暗色主题、中文界面
- **达成 §5 全部性能指标**

不在 MVP：脚本、Runner、OAuth2、WebSocket、Postman 导入（v0.2 立刻补）。

### 6.3 Postman 兼容口径（已确认：对齐最新版）

「按最新的适配」落地为三条明确的目标，避免实现时含糊：

#### 1) 格式版本：Collection Format v2.1.0（draft-07 schema）

核实结果：Postman 官方的最新集合格式仍是 **v2.1.0**，其 schema 目录里当前引用的是 **draft-07** 版本，官方 schema 站点将其标注为稳定、不太会再变（[Postman Schemas](https://schema.postman.com/)、[v2.1.0 draft-07 schema 文档](https://schema.postman.com/collection/json/v2.1.0/draft-07/docs/index.html)）。也就是说「最新」不等于「有个新版本号」，而是：

- **主目标**：v2.1.0 / draft-07，作为唯一的一等公民
- **向下兼容**：v2.0.0 与 v1（旧版导出）自动识别并先升级到 v2.1 再走主流程
- **实现方式**：直接用官方 JSON Schema 做导入前校验，校验失败的文件给出具体字段级报错，而不是笼统的「解析失败」
- **跟随机制**：schema URL 与本地副本一起纳入依赖，CI 每月比对一次官方 schema 是否变更

#### 2) 导出物覆盖：最新版 Postman 客户端能导出什么，我们就要能吃下什么

最新版 Postman 的导出面已经不只是 collection.json，需要逐项覆盖：

| Postman 导出物 | Apogee 处理 | 版本 |
| --- | --- | --- |
| Collection（`*.postman_collection.json`） | 完整导入 | v0.2 |
| Environment（`*.postman_environment.json`） | 导入为 Apogee 环境 | v0.2 |
| Globals（全局变量导出） | 导入为 Apogee 全局变量 | v0.2 |
| **Vault Secrets**（Postman Vault 的密钥导出，支持加密/明文两种 JSON） | 导入为 Apogee 密钥变量，直接写入系统钥匙串；加密格式需用户提供口令 | v0.3 |
| Data Dump（整账号打包导出） | 批量识别目录内所有集合与环境，一次性导入 | v0.3 |
| 目录 / 多文件批量拖入 | 自动分类识别，不要求用户逐个选 | v0.2 |

Vault 是这轮里最值得做的一项：Postman 已把密钥管理做进全部套餐，用户的敏感数据越来越多沉在 Vault 里（[Postman Vault 密钥导入导出](https://learning.postman.com/docs/use/postman-vault/import-export-vault-secrets)）。谁能把 Vault 平滑接过来，谁就真正拆掉了迁移门槛。

#### 3) 脚本兼容：对齐最新 `pm.*` SDK 的高频子集

- 覆盖最新 Postman SDK 中的高频 API（约 Top 30，完整清单见 [03 文档 §7.3](./03-技术架构与数据模型.md)）
- 不支持的调用**不静默丢弃**，转成 `// TODO: apogee 暂不支持 pm.xxx` 并写入《迁移报告.md》
- Postman 内置的 lodash / cheerio / crypto-js 等库不复刻，只提供 `crypto`（hash/hmac/base64）与 `uuid`
- Newman / Postman CLI 的运行语义作为 Apogee CLI（v0.5）的参考，但不承诺命令行参数兼容

#### 明确不支持（导入时提示并跳过，不假装成功）

Monitor、Mock Server、Flows、API 版本管理、协作评论、Postman 生成的 spec 关联关系。这些属于平台能力，见 §2.3 反目标。

> 时间安排未变：**Postman 导入仍排在 v0.2**，v0.1 用 cURL 导入兜底。理由是导入器的质量取决于语料库回归的规模，塞进 MVP 会同时拖慢 MVP 和降低导入成功率。如果你希望它进 v0.1，MVP 周期需要 +2 周，请明确一下。

### 9.3 如何验证本地优先与发布可信度

开源提供了审计起点，但用户还需要能独立核对运行行为和下载产物的证据：

| 手段 | 用户怎么验证 |
| --- | --- |
| 数据完全可见 | 集合以本地文本文件保存，配合公开 Schema；用户可用任意编辑器阅读、备份和迁移 |
| 源码可审阅 | 在公开仓库检查实现、锁文件、CI 配置和变更记录，并可从 tag 自行构建 |
| **网络行为清单** | 官方公开应用会访问哪些域名、何时访问、为何访问；用户可用抓包工具或防火墙核对 |
| **断网可用** | 在断网环境冷启动并跑通核心本地流程；作为 Release 验收项 |
| 无账号 | 核心使用不以账号为前提，减少可关联的个人数据面 |
| 产物可信 | Release 提供 SHA-256、第三方归属声明与 SBOM；Windows 代码签名可选，Release Notes 明确标注签名状态 |
| 漏洞响应 | 与维护者私下协调漏洞修复与披露，避免在公开 Issue 中暴露敏感信息 |

**关键：信任不能只靠声明。** 网络行为清单、断网验收、校验和、SBOM 和签名状态必须写入 Release 验收清单；详见 `docs/release.md`。

### 9.4 商业模式（非首要目标）

MIT 允许商业使用，也允许任何人基于代码提供服务或发行衍生版本；许可证不规定 Apogee 的收入模式。前 12 个月仍以产品质量、口碑和安装体验为先，不以商业化为首要目标。

- **核心客户端保持本地可用**，不以账号、请求次数、导出或离线能力制造付费墙。
- **未来可选服务**：团队密钥同步（端到端加密）、企业策略管控（证书/代理统一下发）和优先支持。
- **不做的商业模式**：广告、强制账号、未明确同意的遥测，或把已经以 MIT 发布的权利再收回。

原则不变：**付费换的是可选的团队协作和支持服务，不是把已有本地功能拿走再卖回来。**

### 9.5 许可证、来源与归属合规

项目自身采用 MIT，并不取消对每个第三方组件的许可证、版权、NOTICE 或源码提供义务。合规要求如下：

## 10. 非功能需求

### 10.1 平台支持

**已确认：v1.0 之前不提供官方 Linux 支持。**

| 平台 | WebView 内核 | 优先级 | 说明 |
| --- | --- | --- | --- |
| Windows 10/11 x64 | WebView2（随系统） | **P0** | 主战场，首发平台 |
| macOS 12+ (Apple Silicon + Intel) | WKWebView | **P0** | 首发平台 |
| Windows ARM64 | WebView2 | P2 | 交叉编译即可，成本低，视需求排 |
| Linux (deb / rpm / AppImage) | WebKitGTK | **不在 v1.0 范围** | 见下方决策说明 |

**Linux 决策说明**

不做 Linux 的收益是实打实的：省掉约 20% 的适配与测试成本，CI 矩阵从 3 平台降到 2 平台，并且规避了 WebKitGTK 这个最容易出性能与渲染意外的内核（PRD §13 R1 的主要来源）。

但要付两笔代价，需要提前规避：

1. **代码不能被 Windows/macOS 绑死。** 架构层面仍按跨平台写：钥匙串走 `keyring` crate 的抽象（Linux Secret Service 后端保留不启用）、路径全部用 `dirs`/`PathBuf`、不引入平台专有 API。**目标是「不测 Linux」，不是「不能跑 Linux」。**
2. **允许社区自行构建，但不把它误报为官方支持。** MIT 源码允许任何人尝试 Linux 构建；维护者不应阻拦或贬低这些工作，也不能因其存在而省略正式平台所需的 CI、视觉回归、漏洞响应和用户支持。当前不提供官方 Linux Release；若未来提供实验性构建，必须明确标为「实验性、未验证、无支持承诺」。

Linux 转正的触发条件：社区构建的反馈与需求达到一定规模，且有资源承担该平台的 CI 与视觉回归。届时按正式平台补齐测试再进主 Release 页面。

**已知风险**：Windows 与 macOS 的 WebView 内核仍不同（Chromium 系 vs WebKit 系），渲染与 CSS 行为存在差异，需要双平台视觉回归测试（见 §12）。

### 10.2 安全与隐私

- **默认零遥测**：不采集任何使用数据。若未来引入，必须默认关闭 + 明确 opt-in + 公开采集字段清单。MIT 源码可供审阅，但发布物仍须用网络行为说明、断网验收、校验和和签名状态提供可验证证据 —— 见 §9.3。
- **密钥不落明文**：密钥类变量通过操作系统钥匙串存储（Windows Credential Manager / macOS Keychain；Linux Secret Service 后端保留但不做验证）；导出时默认脱敏
- **`.gitignore` 自动生成**：创建集合时自动写入，隔离 `*.local.*` 与密钥文件
- **脚本沙箱**：用户脚本运行在受限 JS 沙箱内，无文件系统/进程访问权限，网络访问需显式授权
- **Tauri 能力最小化**：只开启必需的 capability/permission，不放开通用 shell 执行
- **供应链**：依赖锁定 + `cargo-deny`（公告、来源、许可证）/ `pnpm audit` 纳入 CI；发布产物提供 SHA-256、两类第三方归属声明和 SPDX SBOM；Windows 安装程序代码签名可选，未签名状态及系统安全提示须在 Release Notes 中说明。
- **更新机制**：签名校验的增量更新，用户可关闭自动更新

### 10.3 可靠性

- 崩溃不丢数据：编辑内容 300ms 防抖落盘到草稿区，崩溃后恢复未保存标签
- 文件格式向后兼容：v1.0 起承诺 Format v1 稳定，新字段只增不改语义
- 单请求失败不影响其他标签（Rust 侧任务隔离）

### 10.4 无障碍（Accessibility）

- 全键盘可达，焦点可见，Tab 顺序符合视觉顺序
- 语义化 ARIA 标签（Naive UI 组件基础较好，自定义组件需自行补齐）
- 颜色对比度满足 WCAG 2.1 AA（正文 4.5:1，大字 3:1）
- 状态不只用颜色表达（HTTP 状态同时用颜色 + 文字 + 图标）
- 支持系统字号缩放与 `prefers-reduced-motion`

> 完整 WCAG 合规需要辅助技术实测与专业无障碍评审，本文档只覆盖设计层要求。

### 10.5 国际化

- 首发中文简体 + 英文；文案全部走 i18n key，不硬编码
- 日期/数字本地化；UI 布局按最长语言（德语）预留 30% 宽度余量

## 13. 风险与应对

| # | 风险 | 影响 | 概率 | 应对 |
| --- | --- | --- | --- | --- |
| R1 | WebView 跨平台差异导致渲染/行为不一致 | 高 | **中**（不做 Linux 后降级） | 只用保守 CSS 特性；Windows/macOS 双平台 CI 视觉回归；避开实验性 API |

| R3 | Naive UI 是 CSS-in-JS，运行时样式注入影响首屏与主题切换 | 中 | **低↓**（Spike S5 实测首屏 101.9KB，预算占用 68%） | 按需引入 + 静态主题变量 + 模块级 themeOverrides；首屏关键路径不用重组件；**禁止手动 vendor 分包**（S5 发现它会让首屏膨胀 3.4 倍） |

| R9 | 用户数据损坏（文件格式变更/并发写） | 高 | 低 | 原子写（临时文件 + rename）；格式版本号；导入前自动备份 |

| R12 | 外部贡献引入未知来源、凭据或不兼容材料 | 高 | 中 | PR 审阅确认来源权利与无凭据提交；扫描、审阅和私下漏洞沟通共同降低风险 |
