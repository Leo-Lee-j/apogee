# Spike 验证结果汇总

对应 [03 文档 §10](../../docs/03-技术架构与数据模型.md) 的技术风险验证计划。

## 总览

| # | 验证项 | 验收标准 | 结果 | 关键数字 |
| --- | --- | --- | --- | --- |

原计划里「S2 和 S5 是整个架构最大的不确定性」—— 两个都通过了，且余量都不小。**失败预案（S2 退到分片文件 + Blob URL、S5 首屏不挂 ConfigProvider）都不需要启用。**

**真正的意外来自 S1。** 它是唯一 FAIL 的一项，但失败位置不在实现里：Windows 上空壳的 155.7 MB 里 Rust 侧只占 3.71 MB（2.4%），启动的 86% 花在第一行 JS 之前 —— 量到的是 WebView2 的地板。同栈成熟产品 [dbx](https://github.com/t8y2/dbx) 在同一台机器上是 194 MB，高于 xAPI 空壳。结论是 **`启动 < 400ms / 空闲 < 80MB` 这两个门槛（以及 PRD 的 150MB）当初没有实测依据，需要重定**。

**S3 把那个「需要重定」变成了定稿。** 它顺带量了「1 工作区 + 3 标签 + 5000 节点集合树」这个 PRD 声明过但从没测过的条件：**158.8 MB 中位 / 168.6 MB 最差**（5 轮干净启动），其中 `gpu-process` 一个进程占 71.3 MB（45%），Rust 侧只有 3.8 MB（2.4%）。于是内存门槛按平台重定为 **Windows < 220 MB**，并新增 **「Rust 主进程私有常驻 < 20 MB」** 作为唯一真正可控的回归门禁。完整推导见 [03 §10.4](../../docs/03-技术架构与数据模型.md) 与 [PRD §5.1](../../docs/01-产品设计文档.md)。

## 内存门槛：从「待三选一」到定稿

S1 留下的三个选项，S3 给出了判据：

| 选项 | S3 的数据 | 决定 |
| --- | --- | --- |
| (a) 按平台分别定预算 | 默认配置下真实负载 158.8 / 168.6 MB，其中 97% 在 WebView2 进程组 | **采用。** Windows < 220 MB（= 171.5 最差观测 + 28% 余量），macOS 待量测 |
| (b) 从 WebView2 侧找真实节省（关硬件加速） | 关掉能省 **70.6 MB（41.9%）**，压到 98.0 MB；**滚动掉帧率仍是 0%** | **不采用为达标手段。** 见下 |
| (c) 维持 150 MB 并接受不达标 | — | 不采用。S1 已经说过不能默认选这条还继续对外宣称 |

**(b) 为什么可行却不采用**：数字很漂亮，但「没有代价」只在**一种**负载下验证过 —— 文本行列表滚动，而那种负载对合成器极轻（滚动时只更新 35 行纯文本，单步主线程成本占一帧预算 7%）。`--disable-gpu` 是全局开关，CodeMirror 滚动大文档、响应体树大面积重绘、全屏 4K 下的软件合成全会被牵连，这些一个都没测。**拿一个测过的指标去换几个没测过的指标，不叫优化。** 它被记为一项已量化的可选优化（价值 70.6 MB），将来可能作为用户可选的「低内存模式」，但不进默认配置。

顺带纠正一个想当然：**`--disable-gpu` 不会让 `gpu-process` 消失。** 现代 Chromium 退到 SwiftShader 软件光栅化，进程照旧存在，只是从 71.3 MB 缩到 10.7 MB，进程数不变（仍是 7 个）。所以量测台断言的是**实际观测到的进程树 + 命令行里的 flag**，不是「我设过环境变量」。

**另一个反直觉的观测：我们自己的负载几乎量不出来。** 空壳 155.7 MB → 加 1 个工作区 + 3 个标签 + 一棵 5000 节点集合树后 158.8 MB，**只涨 3.1 MB，比跨启动波动（9.1%，约 14 MB）还小**，峰值甚至互有高低（171.5 vs 168.6）。这既说明集合规模不会吃掉内存预算，也说明**「进程树总量」不是有效的回归信号** —— 它自己的噪声就足以盖掉一个几 MB 的真实回归。回归要看 Rust 主进程那条门禁。

## 顺带验证到的架构论点

**按 Range 取响应体首屏分片的耗时与响应体总大小无关。** 1 MB / 10 MB / 50 MB / 100 MB 四档实测均落在 2.9～4.4 ms。对照组把 10 MB 全量拉进 JS 并拼成字符串要 128.9 ms —— 慢 31 倍，而后者正是 Electron 系客户端的实际做法。

这条是「大响应体不卡」的根本原因，不是调参调出来的：磁盘侧是 seek + 定长读，100MB 文件读 64KB 的成本和 64KB 文件相同。

另外，**排除 Monaco 的选型判断成立**：CodeMirror 6 单独一个 chunk 是 107 KB gzip，在所有测试组合下都正确留在懒加载 chunk。Monaco 体积约大一个数量级，进首屏就直接击穿 150KB 预算。

**不打包 Chromium 的体积优势也验证了**：`xapi.exe` 3.96 MB、NSIS 安装包 1.29 MB，只占 15MB 预算的 9%（S1）。但要注意这条**不能推广到内存** —— 体积小和常驻内存小是两件不相干的事，WebView2 虽然不进安装包，运行时仍要 ~152 MB。

**「把成本与规模解耦」这个模式出现了第二次。** S3 里集合树的实渲染行数由视口高度定死（1000 / 5000 / 20000 节点都是 35 行），随规模增长的只剩一趟 O(N) 可见性扫描 —— 20000 节点 0.075 ms，占一帧预算的 0.6%。和 S2 的「Range 取首屏分片耗时与 body 体积无关」是同一个手法：**不是把成本优化小，是让成本不随规模变化。** 两次都是靠这个模式拿到数量级余量，而不是靠调参。

## 工程教训

不是关于 xAPI 的，是关于「怎么做量测」的：

1. **配置项不能有两个来源。** S2 首轮四个用例全部失败于 `TypeError: Failed to fetch`。根因是 CSP 写了两份：`index.html` 的 meta 只放了 `xapi:`，漏了 Windows 上实际使用的 `http://xapi.localhost`（Tauri 在 Windows/Android 把自定义协议映射成 `http://<scheme>.localhost`），协议请求被静默拦掉。已改为 CSP 只由 `tauri.conf.json` 提供。

2. **量测台必须能报告失败，不能只靠超时。** 同一轮里 `CodeMirrorView` 失败时只在界面显示错误、没把失败传回量测台，四个用例各等 30 秒超时且拿不到根因。修法：给组件加 `failed` 事件 + 正式量测前加**协议自检**步骤，把诊断信息在最靠近失败点的地方取出来。

3. **量测台要遵守被测系统自己的约束。** S2 首轮无视 02 §4.4 的分级规则，对 100MB 响应体强行建索引，把 Rust 进程推到 1.4GB —— 测的是一个产品根本不会进入的状态。不过这次副产品很有价值：正是这个数字暴露了索引设计缺陷。

4. **指标必须钉死口径，否则等于没定指标。** S1 第一版按「各进程 `WorkingSet` 求和」报出 **449MB** 空闲内存，差点得出「架构不可行」的错误结论 —— WebView2 子进程映射同一批 msedge DLL，共享页被重复计数，放大 **2.88×**。`PrivateMemorySize64` 也不对，那是提交量不是常驻量（高估 47%）。正确口径是私有工作集（`Working Set - Private`，等于任务管理器「内存」列）。

5. **进程树是需要校验的推断，不是可以直接读取的事实。** Windows 复用 PID，而 `Win32_Process.ParentProcessId` 只是个数字不带世代信息：真父进程退出后它的 PID 可能被我们占用，无关进程就「变成」了后代。S1 中过一次 —— 某轮把另一个应用的 13 个进程算进内存（147MB → **430MB**），**而且 `Stop-ProcessTree` 按同一份名单把它们杀了**。量测台测错可以重跑，动了被测对象之外的东西不行。两道防线：父子边逐条校验创建时间（子不早于父）+ 树内映像名白名单，越界时统计报错、杀进程跳过。

6. **量测台自己要报告环境噪声。** 同一份二进制在有/无背景负载下启动差近 2 倍（545ms vs 1500ms）。S1 的做法：每轮启动前等 CPU 降到 20% 以下再拉起，记录实际起跑负载和「没等到就开跑」的轮次，报告顶部显式声明启动值是上限还是基准。

7. **跨进程计时的起点和终点都不能靠推断。** 终点由被测进程自己上报（应用首帧后写环境变量指定的标记文件，原子 `tmp` + `rename` 并校验 PID）—— 用「窗口出现」会被兜底 `show()` 污染，用「进程存在」在 WebView2 还在加载时就已成立。起点用内核 `Process.StartTime`，不是 `Start-Process` 返回后的秒表（后者高估中位 17ms）。

8. **跨进程/跨语言边界只传纪元数字，不传格式化的时间字符串。** S3 让应用把驻留窗口截止时刻写进阶段文件，第一版用 ISO 8601 字符串，量测台一律报「窗口内只采到 0 个样本」。根因：PowerShell 的 `ConvertFrom-Json` 把 ISO 串自动转成 `DateTime`，再 `[string]` 一次就丢了时区，UTC 值被当本地时间重新解析 —— 截止时刻整整偏掉一个时区偏移量。改成 epoch 毫秒数即正常。S1 的 `readyEpochMs` 本来就是这么做的，这条应当成为规范。

9. **贴着 vsync 的指标是饱和读数，只能证伪不能定量。** S3 第一版报出「1000 / 5000 / 20000 节点首渲都是 26.7ms、fps 都是 75.0、掉帧都是 0%、展开折叠都是 26.7ms」，看着像漂亮结论，实际那些数字全是**显示器节奏**：26.7ms 就是 2 个 vsync（75Hz 下 2×13.3ms）。只要单帧工作量低于一帧预算，任何实现都会报出同一组数 —— 一个只剩 5% 余量的实现和一个有 14 倍余量的实现看起来一模一样。修法：并行报两套口径，不含 vsync 的 `patch` + `layout` + 单步滚动成本（回答「还剩多少余量」，实测 0.9ms / 一帧 7%），以及含 vsync 的「到像素上屏」（回答「用户等了多久」）。

10. **`performance.now()` 被钳到 0.1ms，微量测必须重复取平均。** S3 单次测那趟 O(N) 可见性过滤，三档读出 0.00 / 0.30 / 0.10ms，差点写成「20 倍节点数只慢 1 倍」。那不是数据是量化噪声。重复 200 次取平均后是 0.015 / 0.040 / 0.097ms，趋势才显出来。

11. **量测台不能一边施压一边采样。** 采一次进程树内存要跑两条 CIM 查询，几百毫秒 CPU —— 在帧率量测期间做这件事，测出的掉帧有一部分是量测台自己造的。S3 用两阶段协议：被测应用把进度写进阶段文件，帧率阶段量测台绝不碰进程树；应用跑完进入「驻留窗口」并申报截止时刻，量测台只在窗口内采样，采完校验阶段没变过。顺带发现原采样实现是 O(树大小 × 进程总数)，500+ 进程的机器上单次要一两秒 —— **量测台自己的开销也是噪声源**。

12. **同一个指标在不同状态下不是同一个数，状态必须写进指标定义。** S3 跑完帧率矩阵后立刻量内存得 208.0MB 中位 / 246.2MB 最差，干净启动直接进同一驻留状态得 158.8 / 168.6MB，差的约 50MB 几乎全在 `renderer` 且十几秒不回落。两个数都对，但只有后者能定预算 —— 用前者等于把量测台自己的开销算进产品预算。所以 S3 为每种配置起两组进程，两个数都报，差值本身也是结论。

13. **内存要跨多次启动取值。** 同一份二进制、同一个驻留状态，5 次启动的私有常驻峰值实测跨度 **9.1%**（154.6 / 160.9 / 160.3 / 160.4 / 168.6 MB）—— WebView2 的 GPU/着色器缓存状态不同就能造出这个差。单次启动的数字不足以定门槛，S3 每种配置跑 5 轮取最差观测值。

15. **起跑 CPU 门禁挡不住「整段偏移」型污染。** 重跑 S1 时遇到一次干净的双峰：前 11 轮启动 788～1234ms / 前端 mount 145～219ms，第 12 轮起 553～638ms / 61～74ms，而**每一轮的起跑 CPU 都通过了 20% 门禁**。最可能的原因是刚构建完的二进制被 Defender 首扫。这种污染既躲过了 CPU 门禁（只看瞬时负载），也躲过了「超过中位 2 倍」的离群判定（不是个别离群，是整段偏移）。已给 S1 加**预热漂移检测**：前后两半中位相差超 30% 就在报告顶部标出并指明「用后半段中位或 `-SkipBuild` 重跑」。

14. **配置开关生效与否必须验证，不能相信自己设过。** S3 关硬件加速用 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，量测台会断言那些 flag **确实出现在 WebView2 浏览器进程的命令行上**，否则报错退出。如果开关静默失效，测出来的是「关 GPU 也不省内存」，而这个错误结论会直接否掉一个正确的优化方向。

```bash
node scripts/measure-bundle.mjs          # → s5.json + s5-report.md

# S6：先取语料库，再校验
pwsh -File spikes/s6-postman-schema/fetch-corpus.ps1
cargo run -p s6-postman-schema --release # → s6.json + s6-report.md
```

S1 与 S3 在检测到已有 `xapi.exe` 运行时都会直接拒绝启动（单实例复用会污染结果）；有背景负载时也不会假装数字可信，报告顶部会标注启动值/帧率仅为上限或下限。两者共用 `scripts/lib/ProcessTreeMemory.psm1` —— 进程树遍历、私有工作集口径、CPU 噪声观测只有一份实现，避免两个量测台的口径悄悄分叉。

S3 的两个契约（都是环境变量，Rust 侧读取，正常运行零行为差异）：

- `APOGEE_SPIKE_AUTORUN=s3`（帧率矩阵 + 驻留）或 `s3-mem`（干净启动只驻留）—— **运行时**开关，不是构建期开关。S2 那种 `VITE_AUTORUN_*` 是构建期的，前端产物嵌在 exe 里，换一次开关就要重链一遍 release；而 S3 要在**同一个二进制**上跑 GPU 开/关两种配置，构建期开关既慢又无法保证两轮测的是同一份代码
- `APOGEE_SPIKE_RESULTS_DIR` —— 报告落盘目录。release 二进制的 cwd 是 `target/release`，按 cwd 推断会落到 `target/release/spike-results`，量测台就找不到文件了

## 待做的 Spike

**S4（QuickJS 体积）**，以及 **S1 / S3 的 macOS 侧**。

就绪标记契约（`XAPI_S1_READY_FILE`）与 autorun 契约（`APOGEE_SPIKE_AUTORUN`）已经是跨平台的，Rust 侧无需改动；但 macOS 是 WKWebView，进程模型、内存口径与合成实现都不同，两个量测台都要重写，不能套用本报告的数字。

另外三项不是 Spike 但需要量测：**50 标签内存**（需标签虚拟化落地）、**长时间运行的内存增长**（S3 只观察了十几秒，不能回答「开一天会不会涨」）、**软件合成下 CodeMirror 与响应体树的帧率**（这是「关硬件加速换 70.6 MB」能否被采纳的前置条件）。

热启动那一项（S1 实测 p95 746.3 ms vs 预算 300 ms）也还挂着：量测机有背景负载，需要在空闲机器上复测确认是噪声还是实现问题，再决定修实现还是修指标。它与本次的内存定稿无关。
