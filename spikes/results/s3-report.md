# Spike S3 结果：自研虚拟树的帧率与首渲

## 结论

**PASS。** 5000 节点首渲 **26.8 ms**（预算 100ms，用掉 27%），滚动 **75.0 fps** / 掉帧 **0.00%**（预算 < 5%）；PRD 的「1000 请求集合树 < 100ms」同时达标，实测 **26.6 ms**。失败预案（改用组件库树控件或分页渲染）不需要启用。

**顺带补上 PRD §5.1 一直缺的那个量测条件。** S1 量的是空壳（1 个空标签、无集合），本 Spike 的驻留条件是「1 工作区 + 3 标签 + 5000 节点集合树」—— 比 PRD 声明的「1 工作区、3 标签」还多一棵树。干净启动 5 轮，进程树私有常驻中位 **158.82 MB**、最差 **168.61 MB**（跨轮波动 9.1%），其中 Rust 侧 3.79 MB。对 PRD 的 150MB 预算，这是 **112%** —— **默认配置下预算不可达**，而超出的部分不在我们的代码里（见「发现」的角色分解）。

**关于内存门槛（03 §10.4 选项 b）：关 GPU 能省 70.59 MB（41.9%），足以把内存压回 150MB 预算内（98.01 MB），本 Spike 的滚动场景没测到帧率代价。** 掉帧率 0.00% → **0.00%**（fps 75.0 → 75.0），单步主线程成本 0.90 ms → 0.80 ms。传 `--disable-gpu --disable-gpu-compositing` 之后 gpu-process **仍然存在，只是从 71.29 MB 缩到 10.70 MB**。⚠️ **这个结论只覆盖「文本行列表滚动」一种负载**，而开关是全局的 —— 适用范围见专门一节。

环境：Microsoft Windows 11 专业版 10.0.26200 · Intel(R) Core(TM) Ultra 5 225H · 14 逻辑核 · 内存 31.5 GB · WebView2 Runtime 150.0.4078.105 · node v24.15.0。量测时间 2026-07-31T11:34:31.2330196+08:00，全程 437.3s。
显示器基线：实测 rAF 中位间隔 13.30 ms → **75.2 Hz**（标称 75Hz，119 帧样本，跨度 13.00 ms～13.70 ms）。

## 三条量测口径

1. **帧率按掉帧率判定，不按「fps ≥ 60」判定。** 本机显示器 75.2Hz，也就是说 75 fps 就是物理上限 —— 用「fps ≥ 60」当门槛，一个一帧不掉的实现也可能因采样噪声报出 59.4 而「不达标」。所以先测显示器实际 rAF 节奏（13.30 ms/帧）作为基准，再按相对该节奏掉了多少帧判定，阈值 5%。这也是 Chromium 自己的 smoothness 口径。

2. **滚动由主线程驱动**：每帧写 `scrollTop`，步长 8 行（176px，一次快速 fling 的量级），到边界折返，采 300 帧。真实滚轮在 Chromium 上可以走合成器线程，**主线程驱动是更悲观的一侧**，而且它才会每帧触发我们的 slice 重算 + 行 DOM 更新 —— 那正是要测的东西。固定「行/帧」而不是「总高度/帧数」，是为了让三个档位每帧工作量相同：这样帧时间若随节点数上升，一定是虚拟化本身的问题。

3. **含 vsync 等待的数字和不含的分开报。** `patch`（数据就绪 → Vue 打完 DOM）与 `layout`（读 `offsetHeight` 强制同步排版）不受显示器节奏影响，是「我们的代码有多快」；`首帧`（→ 像素上屏）含最多 2 个 vsync 的等待，是「用户等了多久」。

   **这条不是学术洁癖 —— 不拆就会读错。** 本次自研实现在三个档位的首帧都是 26.6 ms / 26.8 ms / 26.7 ms，看着像「与规模无关」，但那只是 2 个 vsync（26.6 ms）的等待把差异全盖住了。真正的计算成本是 patch 2.80 ms / 3.30 ms / 2.60 ms。同理，帧间隔（p50 一律 13.30 ms）也是**饱和**的：只要单帧工作量低于 13.30 ms，任何实现都会报出相同的 fps 和 0% 掉帧。所以另外测了「单步成本」（`scrollTo` → Vue patch → 强制 layout，不含 paint/composite），它才能回答「还剩多少余量」。

被测对象是**产品组件本身**：`src/components/sidebar/Sidebar.vue`（行高 22px、上下缓冲 10 行，参数与数据形状在 `src/components/sidebar/tree.ts`）。对照组是 `src/spike/S3FullTree.vue（全量 v-for，不虚拟化）`。

## 负载下的进程树内存

驻留条件：**1 工作区 + 3 标签 + 5000 节点集合树（已挂载、空闲）**。S1 量的是空壳（1 个空标签、无集合），这里补上了 PRD §5.1 声明的「1 工作区、3 标签」外加一棵 5000 节点的集合树 —— 比 PRD 的量测条件更重，所以是上界。

**每种 GPU 配置起两次进程**：`mem` 轮干净启动直接进驻留，是稳态；`fps` 轮跑完帧率矩阵再驻留，含一次重负载会话的残留（5 次组件创建/销毁，其中两次铺过 1040 和 5000 行真实 DOM）。**定门槛只能用 `mem` 轮** —— 用 `fps` 轮等于把量测台自己的开销算进产品预算。两个都报，差值就是「一次重会话之后内存回不回来」的答案。

口径与 S1 完全一致（共用 `scripts/lib/ProcessTreeMemory.psm1`）：私有工作集 = `Working Set - Private`，等于任务管理器「内存」列。

**内存跨 5 次启动取值**，门槛按最差观测值定。单次启动不够：同一份二进制两次启动的驻留内存实测能差 9.1%（WebView2 的 GPU/着色器缓存状态不同）。

默认配置下，跑完帧率矩阵之后的驻留内存比干净驻留高 **49.20 MB**（208.03 MB vs 158.82 MB），几乎全部落在 `renderer`（117.14 MB vs 28.11 MB）。十几秒的驻留窗口内没有回落 —— 这不能断定是泄漏（V8 的 GC 不保证及时归还，分离 DOM 也要等下一轮 major GC），但足以说明**「反复创建销毁大列表」这条路径的内存不会立刻还回来**。标签虚拟化（03 §4.2）要按这个前提设计：把标签转 Cold 时卸掉 DOM，不等于内存马上回到基线。

### 这个结论的适用范围（重要）

**本节只证明了一件事：在「文本行列表滚动」这一种负载下，关掉硬件加速没有测到帧率代价。**不能据此推广到「关 GPU 对本产品无害」。三条具体限制：

1. **本量测的负载对合成器很轻。** 自研虚拟树滚动时只更新 35 行纯文本 DOM，单步主线程成本 0.90 ms，占一帧预算 7%。真正吃合成能力的是 CodeMirror 滚动大文档、响应体树的大面积重绘、以及未来的图表 —— 这些都没测。
2. **软件光栅化的代价随重绘面积增长，而窗口大小是用户定的。** 本次窗口是默认 1280×820，量测位只有 240×600。全屏 4K 下的软件合成成本可能是另一个量级。
3. **`--disable-gpu` 是全局开关，不能只对集合树生效。** 一旦关掉，整个应用（含 CodeMirror、未来的 WebGL 图表）都退到软件合成。收益是全局的，代价也是全局的。

## 发现

1. **成本与规模解耦：DOM 量恒定，只有一趟 O(N) 扫描随节点数增长。** 1000 / 5000 / 20000 三档实渲染行数都是 35 行 —— 视口高度定死了这个数，节点数完全不影响它。随 N 增长的只有 `visible` 那趟过滤：0.015 ms / 0.040 ms / 0.097 ms（每档重复 200 次取平均），19 倍节点数换来 6.5 倍耗时 —— 线性，符合预期，而 20000 节点的绝对值仍只占一帧预算的 1%。首渲 patch 三档 2.80 ms / 3.30 ms / 2.60 ms，在噪声范围内持平（跨度 0.70 ms，且不随 N 单调）。这与 S2 的「Range 取首屏分片耗时与 body 体积无关」是同一个架构模式：**把成本与规模解耦，而不是把成本优化小。**

2. **滚动的余量很大，但这一点必须靠单步成本才能看出来。** 三档的帧间隔 p50 一律 13.30 ms、掉帧一律 0% —— 那是**显示器节奏的饱和读数**，不是我们的性能。不受 vsync 影响的单步主线程成本是 1.00 ms / 0.90 ms / 0.80 ms（p95 1.70 ms / 1.60 ms / 1.10 ms），占 13.30 ms 帧预算的 7%。**余量约 14.8 倍**，且不随节点数变化（滚动只重算 `slice`，是 O(视口)；`visible` 被计算缓存挡住不会重跑）。教训是通用的：**在贴着 vsync 的场景里，fps 和帧间隔都是饱和指标，只能证伪不能定量。**

3. **对照组量化了虚拟化的收益，而且收益在首渲不在滚动。** 1040 行时全量 `v-for` 铺 1040 行 DOM、patch 4.60 ms，自研虚拟只铺 35 行、patch 2.80 ms（DOM 节点差 29.7 倍，patch 差 1.6 倍）。5000 行时差距拉开到 patch 22.00 ms vs 3.30 ms（6.7 倍），首帧 146.6 ms vs 26.8 ms —— 全量渲染在这一档已经击穿 100ms 首渲预算。但**滚动**两者都是 0% 掉帧：已经布局好的长列表滚动由合成器处理，主线程不参与。所以虚拟化真正买到的是**首次渲染时间和内存**，不是滚动帧率 —— 这一点和直觉相反，也说明 02 文档 §7.5 第 4 条把集合树列为「必须自研」的理由应当写成首渲与内存，而不是「滚动更流畅」。

4. **展开/折叠是唯一随规模线性增长的交互路径，必须单独盯。** 它走 `all` 换引用 → `visible` 全量重算，是 O(N)。计算成本（patch，不含 vsync）三档中位 2.40 ms / 2.50 ms / 2.80 ms，最长 3.00 ms / 4.60 ms / 3.30 ms；到像素上屏则一律 26.7 ms（＝2 个 vsync，又是饱和读数）。20000 节点下最长 3.30 ms，仍在一帧之内，所以当前实现不需要为展开/折叠做增量更新。**但这是三条路径里唯一会随集合增大而变慢的**，等真实集合突破十万节点就要重新量。

5. **Long Animation Frame：自研实现三档共 0 个超 50ms 的动画帧，对照组 1 个。** LoAF 只上报耗时超 50ms 的帧，所以它是一个「有没有出现卡顿」的二值信号，一个都没有比平均 fps 更能说明滚动过程里没有长帧。对照组那几个落在首次渲染（铺 5000 行 DOM）而不是滚动阶段。

6. **PRD 声明的量测条件第一次被真正量到：168.61 MB，是 150MB 预算的 112%。** S1 只量了空壳（1 个空标签、无集合），中位 146.70 MB；本次干净驻留（1 工作区 + 3 标签 + 5000 节点树）5 轮启动，中位 158.82 MB、最差 168.61 MB，比空壳多 12.12 MB。增量按角色分解：`renderer` +4.88 MB、`gpu-process` +4.28 MB、`host(rust)` +0.11 MB ——**最大的一块在 `gpu-process`，不在我们的代码里**；Rust 侧那 0.11 MB 是 spool 目录与 SpanIndex 缓存的基础结构。含义：03 §4.2 那套「响应体不进内存 / 索引 LRU」管的仍然是 Rust 那几 MB，而预算的分母由 WebView2 决定 —— 与 S1 的结论一致，只是这次是在真实负载下复现的。

7. **关硬件加速能省 70.59 MB（41.9%），而且真的能把内存压回 150MB 预算内（98.01 MB）。** 传 `--disable-gpu --disable-gpu-compositing` 之后 **`gpu-process` 并没有消失** —— 现代 Chromium 会退到 SwiftShader 软件光栅化，进程照旧存在，只是从 71.29 MB 缩到 10.70 MB（省 60.60 MB）。**「关掉硬件加速就少一个进程」是错的**，这也是为什么量测台要断言实际观测到的进程树而不是相信开关。 进程树私有常驻最差值 168.61 MB → 98.01 MB，掉帧率 0.00% → 0.00%，单步主线程成本 0.90 ms → 0.80 ms（差 -0.10 ms）。**所以选项 (b) 技术上是可行的 —— 但可行不等于该做。** 本 Spike 的负载对合成器极轻（滚动时只更新 35 行纯文本，单步成本占一帧的 7%），而 `--disable-gpu` 是全局开关：CodeMirror 滚动大文档、响应体树大面积重绘、全屏 4K 下的软件合成全都会被牵连，这些一个都没测。用「达标」去换一项影响面覆盖整个 UI 而只验证过一种负载的降级，是拿一个测过的指标去赌几个没测过的指标。**建议：不采用 (b) 作为达标手段**，而是把它记为一项已量化的可选优化（省 70.59 MB），等 CodeMirror 与响应体树的合成负载也量过之后再决定是否提供为用户可选开关。

## 未量测 / 边界

- 真实滚轮/触控板滚动：帧率由应用内主线程写 scrollTop 驱动，不经过合成器线程，也不含输入事件延迟。这是更悲观的一侧，但不能宣称为「用户实际手感」。
- paint / composite 的耗时：单步成本只含主线程侧（patch + 强制 layout）。GPU 开关真正影响的合成阶段在另一条线程上，本量测拿不到它的逐帧耗时，只能通过「有没有掉帧」间接判断。
- 50 标签内存（PRD §5.1 < 400MB）：本轮驻留条件是 3 标签 + 一棵 5000 节点集合树，未测 50 标签，也未实现标签虚拟化。
- 磁盘占用（安装后）：本脚本用 --no-bundle 构建，不产出安装包，体积一项仍以 S1 为准。
- macOS：WKWebView 的进程模型、内存口径与合成实现都不同，本报告数字不可套用。
- 长时间运行的内存增长：驻留窗口只有十几秒，不能回答「开一天会不会涨」。
- GPU 关配置下的启动耗时：本脚本不量启动，S1 才是启动的量测台。
- 真实集合数据：节点由 synthTree 合成，名称长度均匀。真实集合里超长接口名会触发文本溢出计算，行内布局成本更高。
- 增量加载：本次一次性把整棵扁平数组交给组件，未测「Rust 侧分页返回 + 滚动到底再取下一页」的路径（那是 v0.2 的实现）。
