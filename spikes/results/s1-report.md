# Spike S1：Tauri 2 空壳冷启动与内存（Windows）

## 结论

**FAIL。** 1 项验收未通过：**PRD-热启动**。

- **PRD-热启动**：热启动 < 300 ms（OS 缓存已热的重启轮次 p95） → 实测 **746.3 ms**（预算占用 249%）

通过的项：PRD-冷启动 608.5 ms / 预算 800ms（76%）；PRD-空闲内存 171.47 MB / 预算 220MB（78%）；PRD-Rust常驻 9.32 MB / 预算 20MB（47%）；PRD-安装包 1.29 MB / 预算 15MB（9%）。

**内存的构成比数值更重要。** 进程树私有常驻中位 155.71 MB 里，Rust 主进程只占 3.71 MB，其余 152.00 MB（98%）在 WebView2 的 6 个子进程里。启动同理：中位 590.3 ms 里前端从第一行 JS 到首帧只占 81.2 ms，**506.5 ms**（86%）花在 JS 之前的进程创建与 WebView2 起进程上，且这段在 20 轮里只波动 436.0 ms～663.6 ms —— 是地板，不是噪声。所以 S1 量到的主要是 **WebView2 在 Windows 上的固定成本**，不是 Apogee 的实现开销。03 文档 §10.1 原来给 S1 定的「启动 < 400ms、空闲 < 80MB」正是因此废弃（定稿见 03 §10.4）；本报告只对 PRD §5.1 的对外承诺判定，外加一条真正可控的「Rust 主进程私有常驻」。

**被测对象是空壳**：1 个空标签、无集合、无 SQLite 连接、无脚本引擎。所有内存数字是**地板值**，不等于 PRD §5.1「1 工作区 3 标签」条件下的达标证明 —— 那个条件由 Spike S3 量（`pnpm spike:s3`，实测 166.2 MB 中位 / 184.9 MB 最差观测）。S1 声明覆盖 Windows + macOS 双平台，macOS 侧未量测。

环境：Microsoft Windows 11 专业版 10.0.26200 · Intel(R) Core(TM) Ultra 5 225H · 14 逻辑核 · 内存 31.5 GB · WebView2 Runtime 150.0.4078.105 · rustc 1.95.0 (59807616e 2026-04-14) · node v24.15.0
量测方式：release 构建（`opt-level="z"` / `lto=fat` / `codegen-units=1` / `panic=abort` / `strip`），20 轮独立进程启动，每轮静置 2000ms 后按 250ms 采样 5 次。量测时间 2026-07-31T11:25:18.4050756+08:00。

量测环境：每轮启动前都等到全核 CPU 降至 20% 以下才拉起进程，实际起跑负载中位 18%、峰值 20%，20 轮全部达标，启动数字可作基准。

### 同机同栈对照：dbx

空壳测出 155.71 MB 之后必须回答一个问题：**这是我们实现得差，还是 WebView2 的地板？** Apogee 自己测不了这个，需要一个同栈的外部参照。[dbx 0.5.70](https://github.com/t8y2/dbx) 是 Tauri + Vue + WebView2 的数据库客户端，**已发布的成熟产品**，实际使用中（已连接数据库、数据网格与 CodeMirror 已加载）。

| 指标 | dbx 0.5.70 | Apogee（空壳） |
| --- | --- | --- |
| 宿主进程私有常驻（任务管理器里应用那一行） | 5.79 MB | 3.71 MB |
| **整棵树私有常驻** | **188.4～194.3 MB** | **155.71 MB** |
| WorkingSet 求和（含共享页重复计数） | 298.5 MB | 448.96 MB |
| 提交量 | 401.2 MB | 224.24 MB |
| 进程数 | 7 | 7 |
| WebView2 启动开关 | 默认配置（无 --disable-gpu / --single-process） | 同为默认配置 |

dbx 的角色分解（私有常驻）：`gpu-process` 81.9 MB、`renderer` 75.1 MB、`browser` 18.6 MB、`utility+crashpad` 6.5 MB。

**结论：地板是 WebView2 的。** 一个功能齐全、带真实负载的同栈产品稳定在 194 MB 左右，反而**高于** Apogee 空壳的 155.71 MB；两者宿主进程都只有几 MB，进程数、WebView2 开关完全一致。这说明 155.71 MB 不是实现质量问题，而是 Windows 上 WebView2 的起步成本；这条对照连同 Spike S3 的负载实测，共同支撑了把 PRD §5.1 的内存预算从 150MB 重定为 **Windows 220MB** —— 定稿见 03 文档 §10.4。

三点使用限制：(1) dbx 是**单次手工快照**对 Apogee 的 20 轮数据，不是受控对比；(2) dbx 带真实负载而 Apogee 是空壳，这个差异对 dbx 不利，所以只能用来支撑「地板很高」，不能用来比较两个产品的优劣；(3) 数字取自同一台机器、同一个 WebView2 Runtime、同一套私有工作集口径，量测于 2026-07-30，换机器需重测。

三个口径在这里给出了**互相矛盾**的排序：按私有常驻 dbx 更高，按 WorkingSet 求和 Apogee 更高，按提交量 dbx 高近一倍。原因是 WorkingSet 含共享页且会被系统按内存压力回收（dbx 已运行一小时被 trim 过，Apogee 是刚拉起的），提交量则是申请量而非占用量。**这正是为什么指标必须钉死口径**：口径选错，同一组数据能得出相反结论。

## 发现

1. **进程树内存不能把各进程的 WorkingSet 加起来。** 同一份数据，WorkingSet 求和 448.96 MB，私有常驻 155.71 MB，提交量 224.24 MB —— 求和口径把真实占用放大了 **2.88×**。原因是 WebView2 的 6 个子进程映射同一批 msedge DLL，共享页在每个进程里各算一次。`PrivateMemorySize64` 也不对，它是提交量而非常驻量。正确口径是性能计数器的 `Working Set - Private`（`Win32_PerfRawData_PerfProc_Process.WorkingSetPrivate`），即任务管理器「内存」列。**本脚本第一版就是按 WorkingSet 求和写的，报出 440MB 空闲内存，差点得出「架构不可行」的错误结论。**

2. **`ParentProcessId` 不能直接用来划进程树，Windows 会复用 PID。** 真正的父进程退出后，它的 PID 可能被我们的 apogee.exe 或某个 WebView2 子进程占用，于是一批无关进程看起来就成了「我们的后代」。本脚本早期版本就中过：某一轮把另一个应用的 13 个进程算进了内存，单轮从 147MB 跳到 430MB；**更严重的是 `Stop-ProcessTree` 按同一份名单把那些进程杀掉了** —— 量测台动了被测对象之外的东西，这比测错数字严重得多。两道防线：父子边逐条校验创建时间（子不早于父），以及树内映像名白名单（只允许 apogee / msedgewebview2），越界时统计直接报错、杀进程直接跳过。教训是通用的：**进程树是一个需要校验的推断，不是一个可以直接读取的事实。**

3. **内存几乎全部是 WebView2 的，Rust 侧只有 3.71 MB。** 进程树私有常驻 155.71 MB 里，WebView2 进程组占 98%，其中单个 `gpu-process` 就要 75.09 MB（占 48%）。两个推论：一是 80MB 这个 Spike 门槛在 Windows + WebView2 上不可达，它是纸面估算而非工程约束（同栈成熟产品 dbx 的对照见上一节）；二是内存预算的分母由 WebView2 定死，Rust 侧每省一 MB 都直接变成余量 —— 这正是 S2 修掉 R13（索引 9.1× 膨胀）的价值所在，也意味着 Rust 侧新增常驻结构要盯得很紧。

4. **启动耗时的主体在 JS 时钟之外，而且它是地板。** 外部计时中位 590.3 ms，前端自报 firstPaint 中位仅 81.2 ms，差值 **506.5 ms**（占 86%）花在「进程创建 → Rust 初始化 → WebView2 起进程 → 加载 HTML/JS」上，且 20 轮只波动 436.0 ms～663.6 ms（跨度 227.6 ms），比总耗时稳定得多。含义很直接：继续压前端首屏 chunk 的边际收益很小（S5 已把首屏做到 101.9KB gzip），真正的杠杆在 WebView2 启动，而那部分不在我们手里。也说明只看 `window.__apogeeBoot` 会系统性低估启动耗时 —— 性能自检面板（PRD §5.2）必须显示外部口径，不能只报前端自计时。

5. **首轮与重启轮次只差 18.5 ms，两者都不是真冷启动。** 首轮 608.5 ms，重启中位 590.0 ms。差距这么小本身就是证据：机器刚跑完构建，二进制、WebView2 运行时、EBWebView 用户数据目录全在 OS 文件缓存里，所谓「首轮」其实也是热的。真正的冷启动会更慢，Defender 首扫新二进制的成本也还没体现。全部轮次跨度 526.2 ms～746.3 ms，单次数字不可引用。

6. **就绪信号必须由被测进程自己发，且时钟要取内核口径。** 跨进程时钟依赖 release 应用在首帧后写 `APOGEE_S1_READY_FILE` 指定的标记（原子 tmp + rename，含 PID 校验）；环境变量不存在时这段代码直接返回，正常运行零开销。两个替代方案都会测偏：用「窗口出现」会被 Rust 侧 3s 兜底 `show()` 污染，用「进程存在」在 WebView2 还在加载时就已成立。起点也不能用 `Start-Process` 返回后的秒表 —— 那个口径本次比内核 `Process.StartTime` 高出中位 19.7 ms，含 cmdlet 开销与 5ms 轮询粒度。

7. **体积是唯一有大量余量的指标。** `apogee.exe` 3.96 MB，NSIS 安装包 1.29 MB，只占 15MB 预算的 9%。前提有两条，都要守住：release profile 保持 `opt-level="z"` + `lto=fat` + `strip`；WebView2 用 `downloadBootstrapper` 不打进安装包。后者的代价是 Win10 无 Runtime 的机器首次安装需要联网，这是产品决策而不是量测问题。

8. **空壳的数字是地板，不是达标证明。** 被测对象没有集合树、没有 SQLite 连接、没有脚本引擎、只有 1 个空标签。PRD §5.1 的量测条件是「1 工作区 3 标签」，空壳稳态中位 155.71 MB（对 220MB 预算 余量 64.29 MB）、峰值 171.47 MB（余量 48.53 MB）。Spike S3 在真实负载（1 工作区 + 3 标签 + 5000 节点集合树）下实测 166.2 MB 中位 / 184.9 MB 最差观测 —— 也就是说**从空壳到真实负载只涨了约 20 MB，其中最大一块还在 gpu-process 而不是我们的代码里**。真正的风险在增量：每个功能落地都要重跑本脚本与 S3，不能等 v0.1 做完再测。

## 未量测 / 边界

- macOS 侧冷启动与内存：S1 声明覆盖双平台，本脚本只跑 Windows。macOS 是 WKWebView，进程模型与内存口径都不同，不能套用本报告的数字。
- 真正的冷缓存启动：未清理 OS 文件缓存、未重启、未排除 Defender 首扫，首轮只是「本次会话首次拉起」。
- PRD §5.1「空闲常驻内存」的量测条件是 1 工作区 + 3 标签；当前空壳只有 1 个空标签，实测值是地板不是达标证明。那个条件由 Spike S3 量（pnpm spike:s3）。
- PRD §5.1「磁盘占用（安装后）< 50MB」：本脚本只量 exe 与安装包体积，未做安装后目录统计（还需计入 EBWebView 用户数据目录）。
- PRD §5.1「50 标签 < 400MB」：需要标签虚拟化落地后才有意义。
- 共享内存的归属：私有工作集刻意排除共享页，因此本报告的数字不包含 WebView2 Runtime 的共享映射；这是「本应用额外占用多少内存」的口径，不是「系统总共为它花了多少」。

## 后续

1. **门槛已定稿（S1 提出，S3 定案），本节不再是待决事项。** 03 文档 §10.1 原来的「启动 < 400ms、空闲 < 80MB」按实测不可达（WebView2 空壳地板就是 155.71 MB / 590.3 ms，其中可控的 Rust 侧只有 3.71 MB），**已废弃**。PRD §5.1 的内存预算按 S3 的负载实测重定为 **Windows < 220MB**（同栈成熟产品 dbx 在 194 MB），并新增 **「Rust 主进程私有常驻 < 20MB」** 作为唯一真正可控的回归门禁 —— 本脚本的门禁表已按此更新。完整推导见 03 文档 §10.4。
2. **「关硬件加速换内存」已量化，但不采用为达标手段。** S3 实测关掉 `--disable-gpu --disable-gpu-compositing` 能省 62.9MB（37.5%），且集合树滚动掉帧率仍为 0%。不采用的理由是证据覆盖面：「没有代价」只在文本列表滚动这一种负载下验证过，而这个开关是全局的（CodeMirror 大文档、响应体树重绘、4K 全屏软件合成都没测）。它记为一项已量化的可选优化，前置条件是先量那几种负载在软件合成下的帧率。顺带纠正一点：**`--disable-gpu` 不会让 `gpu-process` 消失**，只是让它退到 SwiftShader（77.2MB → 10.7MB），进程数不变。
3. **把本脚本接进 CI 性能门禁（PRD §5.2）**：`-Runs 20 -SkipBuild` 复用构建产物，启动或内存回退 > 10% 即 fail。注意 CI runner 的 GPU 进程行为与本机不同，基线要按 runner 单独建。S3（`pnpm spike:s3`）同样要进 CI —— 它才是「真实负载下内存」和「渲染帧率」的门禁。
4. **macOS 侧需要一份等价脚本才能关闭 S1。** 就绪标记契约（`APOGEE_S1_READY_FILE`）已经是跨平台的，Rust 侧无需改动；macOS 上 WKWebView 的进程模型与内存口径都不一样，量测台要重写。
5. **冷启动要拿可对外引用的数字**，需在重启或清文件缓存后单跑一轮，本脚本的首轮不能当冷启动宣称。
6. **`gpu-process` 仍是最大的单一内存项（空壳下 75.09 MB），但它不在我们的控制范围内。** 唯一能动它的手段是关硬件加速，处置见第 2 条。这条留在这里是为了提醒：内存预算的分母由 WebView2 决定，优化只能作用在 Rust 那几 MB 上。
